# UBot

통신 서비스에 관한 질문에 답하고, 상품 탐색부터 매장 방문까지 연결하는 AI 상담 프로젝트입니다.

사용자는 상품과 공지를 살펴보고, AI에게 질문하고, 필요한 매장을 찾을 수 있습니다. 운영자는 상담 결과를 분석해 FAQ와 서비스 정보를 개선합니다.

## 1. 유저 페이지 서비스

- 요금제·결합상품·부가서비스·로밍 상품을 검색하고 상세 정보를 확인합니다.
- 인기·급상승 FAQ에서 자주 묻는 질문을 발견합니다.
- 공지와 장애 안내를 확인하고, 해당 지역의 안내를 배너로 받아봅니다.
- 내 회선과 가입 요금제·결합상품·부가서비스·로밍 정보를 조회합니다.
- 월별 사용량과 청구·납부 내역, 약정·단말 할부 정보를 확인합니다.
- 예약·납부 관련 알림을 조회하고 개별 또는 전체 읽음 처리할 수 있습니다.
- 회원가입·로그인과 내 정보 조회·수정을 제공합니다.

내 이용 정보와 알림은 백엔드 API에 구현되어 있으며, 일부 MY 화면은 연동을 진행 중입니다.
<details>
<summary>예약·납부 알림은 어떻게 만들어지나요?</summary>

1. 예약 확정·취소 시 해당 사용자에게 알림을 기록합니다.
2. 스케줄러가 다가오는 방문 일정과 납부 기한, 기한이 지난 미납 내역을 확인합니다.
3. 조건에 맞는 알림을 중복 없이 생성합니다.
4. 사용자는 알림 목록과 읽지 않은 개수를 확인하고 읽음 상태를 변경할 수 있습니다.
</details>
<details>
<summary>인기 질문과 지역 공지는 어떻게 표시되나요?</summary>

1. 회원의 상담 결과에서 사용된 FAQ를 집계해 인기·급상승 순위를 만듭니다.
2. 순위 결과를 갱신해 화면에서 조회할 수 있게 합니다.
3. 공지 배너는 접속 지역과 게시 조건을 확인해 해당하는 공지·장애 정보를 보여 줍니다.
</details>

## 2. AI 챗봇 서비스

- 회원과 비회원 모두 상담할 수 있습니다. 비회원이 로그인하면 이전 대화 기록을 이어받습니다.
- UBot은 FAQ를 근거로 답하고, 사용한 FAQ를 함께 표시합니다.
- 매장에 관한 질문에는 위치 정보를, 내 정보에 관한 질문에는 로그인한 사용자의 정보를 참고합니다.
- 답할 근거가 없으면 미응답으로 처리합니다. 답변 생성에 실패하면 다시 시도할 수 있고, 이전 대화도 조회할 수 있습니다.
<details>
<summary>AI 답변은 어떻게 만들어지나요?</summary>

1. 질문의 금지어를 확인한 뒤 답변 작업을 접수합니다.
2. 질문을 임베딩해 관련 FAQ를 검색하고, 공식 FAQ 캐시에 적중하면 승인된 답변을 바로 반환합니다.
3. 캐시가 빗나가면 설정된 방식으로 답변 근거를 고릅니다. QUESTION_ANSWER 방식에서는 FAQ 답변을 문장으로 나눠 질문과 유사한 문장만 남깁니다.
4. FAQ의 종류에 따라 일반 FAQ, 근처 매장 정보 또는 사용자 정보를 답변 자료로 모읍니다.
5. AI가 답변을 생성하고 사용한 FAQ를 기록합니다. 적절한 근거가 없으면 AI를 호출하지 않고 미응답 질문으로 남깁니다.
</details>

#### FAQ 랭킹 시스템

UBot은 사용자의 질문에 답변할 때 참고한 FAQ를 기준으로 랭킹을 만듭니다. 최근에 많이 참고된 FAQ는 인기 FAQ, 평소보다 참고 횟수가 크게 늘어난 FAQ는 급상승 FAQ로 보여줍니다.
<details>
<summary>랭킹 시스템 상세 정보</summary>
#### 랭킹이 만들어지는 과정
사용자 질문
  → 답변 생성 성공
  → 질문과 답변에 참고한 FAQ 기록
  → 주기적으로 FAQ별 참고 횟수 집계
  → 인기·급상승·지역별 급상승 순위 계산
  → Redis에 결과 저장
  → GET /rankings에서 조회

#### 무엇을 집계하나요?

답변이 성공하면 질문과 해당 답변에 참고된 FAQ 목록을 기록합니다. 한 답변에서 FAQ 세 개를 참고했다면, 세 FAQ에 각각 기록이 남습니다. 따라서 랭킹의 횟수는 질문 문장이 입력된 횟수가 아니라 FAQ가 답변에 참고된 횟수입니다.

집계에는 로그인한 사용자의 질문만 포함됩니다. 같은 사용자가 최근 집계 시간 안에 같은 질문을 반복하면 첫 질문만 집계합니다. 비회원 질문과 삭제된 FAQ는 랭킹에서 제외됩니다.

#### 순위는 어떻게 정하나요?

| 랭킹 | 기준 |
|---|---|
| 인기 FAQ | 최근 60분 동안 참고된 횟수가 많은 순 |
| 급상승 FAQ | 최근 60분의 참고 횟수가 직전 7일의 평균보다 많이 늘어난 순 |
| 지역별 급상승 FAQ | 해당 시·도의 기록만 사용해 급상승 순위 계산 |

#### 인기 FAQ

최근 60분에 20회 이상 참고된 FAQ 중 횟수가 많은 상위 5개를 보여줍니다.

#### 급상승 FAQ

직전 7일의 참고 횟수를 60분 평균으로 환산한 뒤, 최근 60분의 횟수와 비교합니다.

급상승 배율 = 최근 60분 참고 횟수 ÷ 과거 60분 평균 참고 횟수

예를 들어 직전 7일에 168회 참고됐다면 과거 60분 평균은 1회입니다. 최근 60분에 20회 참고됐다면 20배 급상승한 것입니다.

기본 설정에서는 최근 60분에 20회 이상, 직전 7일에 20회 이상 참고됐으며, 급상승 배율이 20배 이상인 FAQ만 후보가 됩니다. 과거 기록이 기준에 못 미치면 비교 대상에 포함되지 않습니다. 후보 중 배율이 높은 상위 5개를 보여줍니다.

#### 지역별 급상승 FAQ

질문을 받을 때 접속 IP로 시·도를 판별해 기록합니다. 지역별 순위는 최근 기록과 과거 기록 모두 같은 지역의 질문만 사용합니다. 지역을 판별할 수 없는 질문은 전국 랭킹에는 포함될 수 있지만 지역별 랭킹에서는 제외됩니다.

지역마다 별도의 최소 참고 횟수와 급상승 배율 기준을 설정할 수 있습니다. 별도 설정이 없으면 전국 랭킹과 같은 기본값을 사용합니다.

#### 언제 갱신하고 어떻게 조회하나요?

랭킹은 기본적으로 5분마다 다시 계산해 Redis에 저장합니다. GET /rankings는 저장된 인기·전국 급상승·지역별 급상승 결과를 한 번에 반환합니다. 각 결과에는 계산 시각도 포함되므로, 사용자가 조회한 시점과 실제 집계 시점을 구분할 수 있습니다.
</details>

## 3. 매장 서비스

- 주소·매장명·지역·서비스 유형, 현재 위치 또는 지도 범위로 매장을 찾습니다.
- 매장까지 도보·자동차·대중교통 길찾기를 확인합니다.
- 백엔드 API는 방문 가능 시간 조회, 예약·취소·내 예약 조회를 제공합니다. 현재 프론트엔드의 예약 화면은 시연용 UI입니다.
<details>
<summary>매장 검색과 방문 예약은 어떻게 이어지나요?</summary>

1. 입력한 장소나 현재 위치를 기준으로 주변 매장을 검색하고 지도에 표시합니다.
2. 매장을 선택하면 이동 수단에 맞는 경로를 조회합니다.
3. 방문 예약 시 영업시간과 예약 가능 시간을 확인하고 중복 예약을 검사합니다.
4. 예약이 확정되면 알림을 만들고, 방문 시각이 가까워지면 리마인더 알림을 생성합니다.
</details>

## 4. 관리자 시스템

- FAQ·카테고리를 관리하고 변경 이력과 답변에 사용된 FAQ를 확인합니다.
- 미응답 질문을 검토해 새 FAQ로 등록합니다.
- 매장·상품·공지·장애 안내·방문 예약을 관리합니다.
- FAQ 이용 현황과 서비스 운영 지표를 확인하고, 금지어와 비회원 상담 횟수를 설정합니다.
<details>
<summary>미응답 질문은 어떻게 FAQ로 이어지나요?</summary>

1. 답하지 못한 질문을 저장하고 임베딩 유사도에 따라 비슷한 질문끼리 묶습니다.
2. 관리자가 질문 묶음과 기존 FAQ 이용 현황을 확인합니다.
3. 필요한 내용을 새 FAQ로 등록하거나 기존 FAQ를 수정합니다.
4. FAQ 벡터를 생성·백필하면 이후 상담 검색에 반영됩니다.
</details>

## 1. 유플러스 챗봇을 직접 사용해보니, 장소 관련 질문을 하면 챗봇에서 직접 해당 장소를 안내해주는게 아니라 매장 찾기 페이지로 연결을 해줍니다. 다른 회사의 챗봇 서비스들도 비슷하게 작동하는데, 혹시 이렇게 구현하는 이유가 있을까요?

- 현업에서는 이미 구축된 기능을 배제할 필요가 없다는 의견
- 챗봇 내부에 지도 표시 기능을 새로 추가하기보다, 기존 매장 안내 기능을 활용하는 편이 개발 측면에서 더 용이할 수 있다는 설명

## 2. 실제 AI 상담 서비스를 운영할 때, 사용자의 질문이 명확하지 않아 답변을 어떻게 해야하는지 모르는 경우가 많을 것 같습니다. 이런 경우 질문을 하냐 마냐 경계를 정하는 기준이 있을것 같은데, 현업에서는 LLM이 어떻게 기준을 정하게 하는지 궁금합니다.

- 모든 서비스에 공통으로 적용되는 단일 기준값이나 정답의 부재
- 기획 단계에서 서비스별 시나리오와 예외 처리 원칙을 정의하는 방식
- 특정 서비스 예시: 로밍 서비스
    - 사용자가 할 법한 질문과 대화 시나리오의 사전 정리
    - 시나리오별 필요 업무 API 준비
    - AI 검색·LLM의 요청 시나리오 분기
    - 업무 시스템의 API 기반 처리
- 준비된 시나리오 밖의 질문 또는 유사도 기반 답변이 어려운 질문에 대한 사전 정책 필요
    - 일정 유사도 이상일 때 답변 여부
    - 조건에 맞는 답변이 없을 때 상담 연결 여부
    - 고객 안내 문구
- 프로젝트 차원의 답변·상담 연결·미답변 처리 기준 명문화 필요성 강조

## 3. 저희가 만든 임베딩 모델의 유사도 threshold를 실험으로 정하고 있는데, 실무에서는 threshold를 어떤 기준으로 정하고, 추후에 변경한다면, 어떤 이유에 근거해서 변경하는지 궁금합니다.

- 유사도가 높더라도 정답을 보장하지는 않는다는 점
- 테스트 결과 기반의 Threshold 설정 필요
- 정답·오답 사례 검증을 통한 적정 임계값 도출
- Threshold 선정 근거의 명확화 필요
    - 실험 방식
    - 실험 결과
    - 해당 임계값을 선택한 이유
- Threshold 변경 시에도 성능 측정 결과와 운영상 오류 사례를 근거로 한 변경 사유 제시 필요

## 4. 임베딩 방법중에, Dense, Sparse, Multi-vector 세개가 있다고 알고 있습니다. 실무에서는 성능 개선을 위해 가벼운 파트에는 Dense만, 복잡한 파트에는 여러 방법을 섞은 hybrid방식을 사용할 것 같은데, 가벼운 파트와 무거운 파트를 어떤 기준으로 구분하는지 궁금합니다.

- AI 검색·LLM 기반 검색 구현 경험 부족으로, 가벼운 작업과 복잡한 작업을 나누는 구체적인 실무 기준에 대한 답변 한계
- 다른 팀의 요청 특성별 모델 오케스트레이션 준비 사례 언급
    - 단순 요청: 경량 모델 사용
    - 높은 수준의 추론 필요 요청: 고성능 모델 사용
- 모델·서버 비용의 경우, 기능 필요성과 성능 검증 자료를 근거로 비용 부서와 협의 및 승인 진행

## 6. 저희는 미답변 로그를 클러스터링해서 신규 FAQ 후보를 발굴하려고 하는데, 실무에서 이런 '콘텐츠 갭 발견' 파이프라인을 실제로 운영해보신 경험이 있으신가요?

- 미답변 로그 클러스터링을 통한 신규 FAQ 후보 발굴 경험 부재
- 기능 자체에 대한 긍정적 평가와 운영 모니터링 체계의 중요성 강조
- 유사 사례: 고객 참여형 서비스의 댓글 운영
    - 욕설·무관한 내용·부적절한 표현 사전 필터링
    - 신고 콘텐츠 또는 특정 조건 콘텐츠에 대한 운영자 알림
    - 운영자 검토 및 조치를 위한 관리 장치 마련
- 미답변 질문 관리 적용 방향
    - 미답변 질문 목록화
    - 관리자 검토
    - 확인된 질문의 FAQ DB 추가
    - 처리 완료·미완료 상태 관리
- 실서비스 운영 측면의 유용성 언급

## 7. 임베딩 모델을 추가 데이터로 파인튜닝해본 경험이 있으신가요? 사전학습 모델 그대로 쓰는 것과 비교해서 실제로 유의미한 개선이 있었나요?

- 사전학습 모델 대비 파인튜닝 효과의 정량적 비교 사례 부재
- 실무의 주요 제약 요인으로서 보안 이슈 언급
    - AI 활용 시 보안팀 검토 필요
    - 외부 모델 대신 로컬 환경 활용 방식 준비
    - 요청 특성별 경량 모델·고성능 모델 선택 오케스트레이션 검토

## 8. LLM 모델 평가 지표를 확정하기 어려웠습니다. 한국어를 지원하는 모듈도 많지 않았고 정확도가 다소 떨어진다고 판단했습니다. LLM이나 인간이 JUDGE 하지 않고, 한국어 능력이나 정보의 정확도를 정확하게 따질 수 있는 테스트 기준을 찾기 어려웠습니다. 실무에서는 LLM 성능을 어떻게 평가하는지 궁금합니다.

- LLM 평가 전문 경험 부족
- 프로젝트 목적에 맞는 평가 기준과 수치의 직접 정의·검증 방식 제안
- 업무 담당자가 실제 요구사항과 정답을 알고 있을 때 가능한 판단
    - LLM 답변의 업무 적절성
    - 예상 답변·처리 결과 충족 여부
- 권장 평가 방식
    - 질문과 정답이 정해진 테스트셋 준비
    - 답변 정확도 측정
    - 기대 답변과의 유사성 측정
    - 미답변·오답 여부 측정
- 회사 내부 환경
    - 보안상 사용 가능 LLM의 사전 제한
    - 여러 모델 간 비교보다 허용 모델의 로직 수행 및 예상 결과 충족 여부 중심 평가

## 긍정적으로 평가한 요소

### 자주 묻는 질문·연관 질문 추천

- 사용자의 첫 질문에 관련 질문을 함께 제시하는 기능의 유용성
- 벡터 검색 또는 키워드 기반 구현 가능성 언급

### 미응답 질문 관리

- 가장 구체적으로 긍정 평가한 운영 기능
- 관리자 페이지 기반의 미응답 질문 목록화·검토·FAQ 반영·처리 상태 관리
- 실서비스 운영 측면의 높은 활용 가능성

### AI 챗봇과 실제 서비스 연결

- 매장 안내, 매장 예약, 상담 가능 시간 안내, 예약 신청 알림 등 실제 서비스 흐름 연결 방안에 대한 긍정적 의견
- 단순 정보 제공을 넘어 업무·예약 흐름까지 처리하는 기능의 차별화 가능성

### 지역·주제별 이상 징후 감지

- 특정 지역에서 동일·유사 문의가 급증할 때 지도에 표시하고 담당자에게 알리는 기능의 긍정적 평가
- 특정 지역의 장애 문의 급증 시 네트워크·송신탑 이슈 가능성을 담당자에게 전달하는 방식
- 지역 단위뿐 아니라 전국 단위의 급증 패턴 감지 및 관리자 알림 가능성
