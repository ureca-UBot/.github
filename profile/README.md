# UBot

통신 서비스에 관한 질문에 답하고, 상품 탐색부터 매장 방문까지 연결하는 AI 상담 프로젝트입니다.

사용자는 상품과 공지를 살펴보고, AI에게 질문하고, 필요한 매장을 찾을 수 있습니다. 운영자는 상담 결과를 분석해 FAQ와 서비스 정보를 개선합니다.

## 1. 유저 페이지 서비스

- 요금제·결합상품·부가서비스·로밍 상품을 검색하고 상세 정보를 확인합니다.
- 인기·급상승 FAQ에서 자주 묻는 질문을 발견합니다.
- 공지와 장애 안내를 확인하고, 해당 지역의 안내를 배너로 받아봅니다.
- 내 회선과 가입 요금제·결합상품·부가서비스·로밍 정보를 조회합니다.
- 월별 사용량과 청구·납부 내역, 약정·단말 할부 정보를 확인합니다.
- 예약·납부 관련 알림을 조회하고 개별 또는 전체 읽음 처리할 수 있습니다.
- 회원가입·로그인과 내 정보 조회·수정을 제공합니다.

<summary>알림은 언제 생성되나요?</summary>

---

#### 알림 종류

| 구분 | 알림 | 시점 |
|---|---|---|
| 방문 예약 | 예약 확정·취소 | 예약이 확정되거나 취소될 때 |
| 방문 예약 | 방문 리마인더 | 방문 24시간·6시간·1시간 전 |
| 요금 | 납부 기한 임박·연체 | 납부 기한이 가까워지거나 지났을 때 |
| 로밍 | 로밍 시작·종료 | 시작일과 종료일의 하루 전·당일 |
| 약정·할부 | 만료 임박 | 만료 30일·7일·1일 전 |
| 데이터 | 사용량 도달 | 이번 달 데이터 사용량이 80%·100%에 도달했을 때 |

#### 어떻게 만들어지나요?

```text
스케줄러 (Asia/Seoul 기준 cron, ShedLock으로 한 인스턴스만 실행)
  ├─ 방문 예약 리마인더          매시 정각
  ├─ 요금 납부 리마인더          매일 09:00
  ├─ 로밍·약정·할부 리마인더     매일 09:00
  └─ 데이터 사용량 리마인더      매시 정각
       └─ 대상 조회 (활성 가입, 탈퇴하지 않은 사용자만)
            └─ 남은 기간에 맞는 단계 하나 선택
                 └─ 단계가 들어간 중복 방지 키로 알림 저장 (이미 있으면 건너뜀)
```

- 알림마다 `dedupe_key`(예: `CONTRACT_EXPIRING:{id}:D7`)를 두고, DB의 `INSERT ... ON CONFLICT DO NOTHING`으로 저장합니다. 스케줄러가 다시 돌거나 서버가 여러 대여도 같은 알림이 두 번 생기지 않습니다.
- 남은 기간이 여러 단계에 걸치면 가장 짧은 단계 하나만 보냅니다. 예를 들어 만료까지 5일 남았다면 30일 전·7일 전 알림이 아니라 7일 전 알림 한 건입니다.
- 이미 지난 단계의 알림은 만들지 않습니다. 만료 3일 전에 등록한 약정에는 30일 전·7일 전 알림을 소급해서 보내지 않습니다.
- 데이터 사용량은 이번 달 사용량이 기준(80%·100%) 이상인 가입만 조회해 단계별로 한 번씩 알립니다. 무제한 요금제는 대상이 아닙니다.

<details>
<summary>공지와 장애 안내는 어떻게 보이나요?</summary>

---

- 공지(`NOTICE`)와 장애(`OUTAGE`)를 같은 구조로 관리하고, 관리자가 제목·내용·대상 지역(시·도)·종료 시각을 정해 등록·수정·삭제합니다.
- 대상 지역을 비워 두면 전국에 노출되고, 지역을 정하면 그 지역에서 접속한 사용자에게만 보입니다. 접속 IP로 시·도를 판별하며, 판별할 수 없으면 전국 안내만 보여 줍니다.
- 종료 시각을 정하지 않으면 계속 노출되고, 정하면 그 시각이 지난 안내는 배너에서 자동으로 빠집니다.
- 사용자는 비회원도 `GET /notices/banners`로 현재 노출 중인 공지·장애 배너를 한 번에 받습니다. 목록은 유형과 지역으로 걸러 볼 수 있고, 상세는 별도 API로 확인합니다.

## 2. AI 챗봇 서비스

- 회원과 비회원 모두 상담할 수 있습니다. 비회원이 로그인하면 이전 대화 기록을 이어받고, 회원은 지난 대화방을 골라 이어서 질문할 수 있습니다.
- UBot은 FAQ를 근거로 답하고, 사용한 FAQ를 함께 표시합니다.
- 매장에 관한 질문에는 위치 정보를, 내 정보에 관한 질문에는 로그인한 사용자의 정보를 참고합니다.
- 답할 근거가 없으면 미응답으로 처리합니다. 답변 생성에 실패하면 다시 시도할 수 있고, 이전 대화도 조회할 수 있습니다.
- 답변이 질문의 의도와 다르면 로그인 사용자가 의도(일반·매장·내 정보)를 직접 골라 같은 질문을 한 번 다시 검색할 수 있습니다.
<details>
<summary>의도별 재검색은 어떻게 동작하나요?</summary>

---

#### 왜 필요한가요?

FAQ는 질문 의도(일반 / 매장 데이터 필요 / 사용자 데이터 필요)에 따라 처리 방식이 다릅니다. 검색이 질문과 다른 의도의 FAQ를 찾아 엉뚱한 답이 나오면, 사용자가 의도를 직접 골라 그 의도의 FAQ만 대상으로 다시 검색합니다.

#### 흐름

```text
성공한 답변에서 사용자가 의도 선택 (예: 매장 데이터 필요)
  └─ POST /chat/questions/research  (원본 답변의 키 + 의도 + 선택적 현재 위치)
       └─ 원본 확인: 본인의 성공한 답변인지, 이미 재검색한 의도는 아닌지
            └─ 원본과 섞이지 않는 새 시도 생성 (원본 연결, 질문·대화는 원본에서 복사)
                 └─ 작업 접수 → 즉시 202 + jobId 응답, 현재 위치·접속 지역은 작업에 담아 Worker로 전달
                      ↓
                 답변 Worker가 선택한 의도의 FAQ 질문 표현(유사표현 포함)만 검색
                      └─ 이후는 일반 질문과 같은 처리
                         (유사도 기준 판정 → 의도별 자료 수집 → LLM 답변)
                      ↓
                 화면이 GET /chat/jobs/{jobId}로 결과 조회
```

#### 규칙

| 규칙 | 내용 |
|---|---|
| 대상 | 로그인 사용자만. 성공한 답변이고, 재검색으로 만들어진 답변이 아닐 때만 가능 |
| 횟수 | 같은 질문의 같은 의도는 한 번만. 서버 확인과 DB의 부분 유니크 인덱스(`source_attempt_id`, `intent`)로 동시 요청까지 막음 |
| 위치 | 매장 의도에서 현재 위치를 쓸 때만 위도·경도를 함께 보냄 (선택) |
| 응답 | 일반 질문과 같은 비동기 방식. 재검색 시도의 새 `idempotencyKey`와 `jobId`를 돌려줌 |
| 캐시 | 일반 의도는 공식 답변 캐시 대상(켠 경우). 매장·내 정보 의도는 맥락이 필요해 캐시를 건너뜀 |
| 재시도 | 재검색 답변은 재시도 불가. 실패하면 다른 의도를 고르게 함 |
| 미응답 처리 | 재검색이 실패해도 미응답 질문으로 쌓지 않음. 사용자가 의도를 직접 골라 FAQ 부족 신호로 보기 어렵기 때문 |
| 집계 | 비회원 질문 횟수와 질문 로그 순위 집계에 중복으로 잡히지 않음 |

---
</details>

#### 채팅 처리

- 회원과 비회원의 질문을 받아 답변 작업을 비동기로 처리합니다. 질문을 접수하면 작업 번호를 먼저 반환하고, 화면은 해당 작업의 처리 상태와 최종 답변을 조회합니다.
- 회원은 자신의 대화방과 이전 메시지를 조회하고 이어서 질문할 수 있습니다. 비회원의 대화는 세션으로 구분하며, 로그인하면 해당 대화를 회원에게 연결합니다.
- 답변 시도별 처리 결과와 실패 사유를 기록하고, 재시도가 허용된 실패에 대해서만 다시 답변을 생성합니다.

<summary>채팅은 어떻게 처리되나요?</summary>

---

#### 질문 접수부터 답변 조회까지

```text
사용자가 질문 전송
  └─ 회원 인증 또는 비회원 세션 확인
       └─ 대화방과 답변 시도·작업 저장
            └─ HTTP 202 + jobId 반환
                 ↓
            Worker가 답변 작업 처리
              ├─ 입력 가드로 검색에 사용할 질문 준비
              ├─ FAQ 검색과 답변 자료 수집
              └─ 답변 생성·검사
                 ↓
            처리 결과와 답변 저장
                 ↓
화면이 GET /chat/jobs/{jobId}로 상태와 최종 답변 조회
```

FAQ 검색 이후에는 공식 FAQ 캐시 사용 여부와 검색 결과에 따라 처리 경로가 달라집니다. 공식 FAQ 캐시에 적중하면 등록된 답변을 반환하고, LLM으로 답변을 생성하는 경우에는 출력 가드를 거칩니다.

#### 주요 처리 규칙

| 구분 | 내용 |
|---|---|
| 비동기 처리 | 질문을 받는 요청과 실제 답변 생성 작업을 분리하고, 작업 번호로 결과를 조회 |
| 대화 구분 | 회원은 사용자와 대화방을 기준으로, 비회원은 세션에 연결된 대화를 기준으로 처리 |
| 조회 권한 | 회원은 자신의 작업·대화만, 비회원은 해당 세션의 작업만 조회 |
| 대화 연결 | 비회원이 로그인하면 세션의 대화를 회원에게 연결 |
| 질문 보존 | 사용자가 입력한 원문을 보관하고, 검색·답변 생성에는 입력 가드를 통과한 질문을 사용 |
| 재시도 | 실패한 답변 중 허용 조건과 횟수를 만족하는 경우에만 새 시도 생성 |
| 재시도 제한 | 처리 중이거나 이미 성공한 작업, 출력 가드가 거절한 답변 등은 재시도하지 않음 |

---

</details>

#### 입력·출력 가드

- 입력 가드는 질문을 독립된 요청 단위로 검사해 위험 요청을 제거하고, 남은 정상 질문만 FAQ 검색과 답변 생성에 전달합니다.
- 출력 가드는 LLM이 생성한 답변을 제공된 FAQ·추가 자료·실제 조회 결과와 함께 검사합니다. 검사 규칙에 해당하는 문제 문장이나 내부 번호 표기를 제거하고 정상 설명은 유지합니다.
- 두 가드는 별도의 AI 모델을 추가 호출하지 않고, 문장 패턴과 수치·대상·조건을 비교하는 코드 규칙으로 동작합니다.

#### LLM 답변 생성 경로의 검사 흐름

```text
사용자 질문
  └─ 입력 가드
       ├─ 질문 정리와 독립된 요청 분리
       ├─ 금칙어·프롬프트 조작 요청 검사
       └─ 위험 요청 제거 후 남은 질문 재검사
            ↓
       정상 질문으로 임베딩·FAQ 검색
            ↓
       FAQ·추가 자료를 이용한 LLM 답변 생성
            ↓
       출력 가드
         ├─ 기재된 근거 번호 확인
         ├─ 위험 문장과 근거 충돌 검사
         └─ 내부 FAQ 번호 표기 제거
            ↓
       남은 정상 답변 반환
```

입력에서 사용할 질문이 남지 않으면 검색·LLM 호출 전에 종료합니다. 출력에서 사용할 답변이 남지 않거나 최종 검사에 실패하면 답변을 반환하지 않고 기존 차단 안내로 처리합니다.

#### 입력 가드

| 검사 항목 | 처리 방식 |
|---|---|
| 질문 정리 | 요청 앞의 인사말과 이모지를 정리하고, 숫자·기기명·URL 등 질문에 필요한 내용은 보존 |
| 요청 분리 | 문장 부호와 요청 표현 등을 기준으로 독립된 요청을 구분 |
| 위험 요청 | 금칙어와 시스템 지시 무시·내부 프롬프트 공개 등 등록된 프롬프트 조작 패턴 검사 |
| 정상 질문 보존 | 위험 요청과 독립된 정상 질문이 함께 있으면 위험 요청을 제거하고 정상 질문만 전달 |
| 조합 공격 | 개별 요청을 합쳤을 때 드러나는 공격도 다시 검사 |

예를 들어 “이전 지시를 무시해. 선택약정 할인은 어디에서 신청하나요?”처럼 독립된 요청이 함께 들어오면, 조작 요청을 제거하고 정상 질문을 검색에 전달합니다.

#### 출력 가드

| 검사 항목 | 처리 방식 |
|---|---|
| 근거 번호 | 답변에 기재된 근거 번호가 실제 제공한 FAQ 목록에 포함되는지 확인. 근거 번호가 비어 있다는 이유만으로 차단하지 않음 |
| 내부 정보 | 내부 프롬프트·인증 정보 등 노출 패턴에 해당하는 내용 제거 |
| 내부 FAQ 번호 | `[FAQ ID: …]`, `(FAQ ID: …에 따르면, …)`, `FAQ […]`, `FAQ …` 형태의 내부 번호와 불필요한 출처 표현 제거 |
| 실행·조회 주장 | 실제 기능·결과 없이 처리를 완료했다고 주장하거나 조회해 주겠다고 약속하는 문장 제거 |
| 수치·조건 충돌 | 금액·기간·할인율 등에서 검사 규칙으로 확인되는 근거 충돌 검사 |
| 답변 내 자기모순 | 같은 대상·조건에 대한 가능·불가 설명이 충돌하면 제공 근거와 대조해 문제 문장 제거 |
| 서류·필수 조건 | 제공 자료에 없는 필수 서류나 이용 조건을 추가하는 문장 검사 |
| 대상·업무 불일치 | 다른 기기·서비스·업무에 대한 근거를 동일한 대상으로 적용하는 문장 검사 |
| 근거 없는 제한 | 제공 자료로 확인되지 않는 불가·미지원·제한 단정 검사 |

#### 정상 안내를 보존하는 기준

- FAQ라는 단어 자체는 금지하지 않습니다. 내부 번호 표기와 출처 표현을 정리하고, 같은 문장에 있는 정상 설명은 남깁니다.
- 금액·기간·할인율·전화번호는 내부 FAQ 번호와 구분합니다.
- 사용자가 앱이나 고객센터에서 직접 확인하도록 안내하는 문장과 실제 조회 결과에 근거한 설명은 구분해 처리합니다.
- 대상이나 조건이 다른 설명을 같은 대상의 모순으로 취급하지 않습니다.
- 문제 문장을 제거한 뒤 그 문장에만 의존하는 결론이 남지 않도록 후속 문장도 확인합니다.

FAQ와의 비교는 정의된 표현·수치·대상·조건을 검사하는 방식입니다. 답변 전체의 의미와 모든 사실관계를 AI처럼 판정하는 구조는 아닙니다.

#### FAQ

- UBot의 FAQ는 대표 질문과 답변을 중심으로 카테고리, 질문 유형, 유사표현을 함께 관리합니다. 대표 질문과 유사표현은 각각 벡터로 변환해 faq_embeddings에 저장합니다. 덕분에 사용자가 다양한 표현으로 질문해도 같은 FAQ의 답변을 찾을 수 있습니다.

#### FAQ 한 건에는 무엇이 들어가나요?

| 구성 요소 | 역할 |
|---|---|
| 대표 질문 | 관리자가 등록한 FAQ의 기준 질문 |
| 답변 | 챗봇이 답변을 만들 때 참고하는 내용 |
| 카테고리 | 관리자가 FAQ를 분류하기 위한 항목 |
| 질문 의도 | 일반 질문·사용자 데이터 필요·매장 데이터 필요 등 처리 방식을 구분 |
| 유사표현 | 대표 질문과 같은 의미를 가진 다른 질문 표현 |
| 캐싱 유무 | 캐싱이 가능한 FAQ인지 아닌지 구분 |
| 버전 | FAQ가 수정됐을 때 버전 업 |

#### FAQ와 검색용 데이터는 어떻게 연결되나요?
```text
FAQ 한 건 (faq)
  ├─ 대표 질문·답변·카테고리·질문 유형
  │
  └─ 질문 표현 목록 (faq_question_variants)
       ├─ 대표 질문
       ├─ 유사표현 1
       └─ 유사표현 2
            │
            └─ 각 표현의 벡터 저장 (faq_embeddings)
                 ├─ QUESTION: 질문 표현만 임베딩
                 └─ QUESTION_ANSWER: 질문 표현과 FAQ 답변을 함께 임베딩
```

대표 질문도 유사표현과 마찬가지로 질문 표현 목록에 저장됩니다. 각 표현은 원본 FAQ에 연결되며, 그 표현의 벡터는 faq_embeddings에서 관리합니다. 벡터에는 질문 표현, 임베딩 설정, 벡터 유형, FAQ 버전이 연결되어 있어 검색할 때 현재 FAQ에 맞는 벡터를 사용할 수 있습니다.

#### 등록부터 사용자 답변까지

관리자가 FAQ 등록
  └─ 대표 질문·답변·분류·유사표현 저장
       └─ 각 질문 표현의 벡터를 faq_embeddings에 저장
            ↓
       사용자가 챗봇에 질문
            ↓
       사용자 질문과 FAQ 질문 표현의 벡터 유사도 비교
            ↓
       가장 가까운 표현이 연결된 FAQ 검색
            ↓
       원본 FAQ의 답변을 활용해 응답

한 FAQ의 여러 표현이 검색되더라도 가장 유사한 표현의 점수로 FAQ를 한 번만 결과에 올립니다. 현재 사용자 질문의 FAQ 검색에는 QUESTION 벡터를 사용합니다.

#### 유사표현은 어떻게 준비하나요?

관리자는 대표 질문을 로컬 LLM에 전달해 같은 의미의 한국어 질문을 최대 10개 제안받을 수 있습니다. 제안된 표현을 확인한 뒤 FAQ 등록·수정 요청에 포함하면 원본 FAQ의 유사표현으로 저장됩니다.

예를 들어 대표 질문이 “요금제를 변경하려면 어떻게 하나요?”라면 “요금제 바꾸는 방법 알려줘”를 유사표현으로 로컬LLM이 추천해줍니다. 개별적으로 입력할 수도 있으며, 추천한 유사표현을 그대로 사용할 수 있습니다. 각 유사표현들의 질문들의 답변은 원본 답변 하나입니다.

#### FAQ를 수정하면 어떻게 되나요?

FAQ를 수정하면 버전이 올라갑니다. 대표 질문이나 유사표현이 바뀌면 질문 표현 목록과 faq_embeddings의 벡터를 함께 갱신합니다. 답변이 바뀌면 질문과 답변을 함께 임베딩한 QUESTION_ANSWER 벡터에도 새 답변을 반영합니다.

#### FAQ 랭킹 시스템

- UBot은 사용자의 질문에 답변할 때 참고한 FAQ를 기준으로 랭킹을 만듭니다. 최근에 많이 참고된 FAQ는 인기 FAQ, 평소보다 참고 횟수가 크게 늘어난 FAQ는 급상승 FAQ로 보여줍니다.
<details>
<summary>랭킹 시스템 상세 정보</summary>

---

#### 랭킹 시스템 흐름

```text
사용자 질문
  └─ 답변 생성 성공
       └─ 질문과 답변에 참고한 FAQ 기록
            └─ 집계 대상 확인
                 └─ 로그인 사용자, 중복 방지를 위해 최근 60분 간 동일한 질문은 1개만 랭킹 처리
                      └─ FAQ별 참고 횟수 집계
                           │
                           ├─ 인기 FAQ
                           │    └─ 최근 60분에 20회 이상 참고된 FAQ
                           │         → 참고 횟수가 많은 상위 5개
                           │
                           ├─ 전국 급상승 FAQ
                           │    └─ 최근 60분 횟수 ÷ 직전 7일의 60분 평균
                           │         → 최근·과거 각각 20회 이상 기록, 과거 대비 증가율 20배 이상인 상위 5개
                           │           
                           │
                           └─ 지역별 급상승 FAQ
                                └─ 같은 시·도의 기록만 사용해 급상승 배율 계산
                                     → 지역별 별도 기준 적용
                                     → 기준을 통과한 상위 5개
                           ↓
                    Redis에 랭킹 결과 저장 (스케쥴러가 5분마다 갱신)
                           ↓
                    GET /rankings로 한 번에 조회
```

#### 무엇을 집계하나요?

답변이 성공하면 질문과 해당 답변에 참고된 FAQ 목록을 기록합니다. 한 답변에서 FAQ 세 개를 참고했다면, 세 FAQ에 각각 기록이 남습니다. 따라서 랭킹의 횟수는 질문 문장이 입력된 횟수가 아니라 FAQ가 답변에 참고된 횟수입니다.

집계에는 로그인한 사용자의 질문만 포함됩니다. 같은 사용자가 최근 집계 시간 안에 같은 질문을 반복하면 첫 질문만 집계합니다. 비회원 질문과 삭제된 FAQ는 랭킹에서 제외됩니다.

#### 순위는 어떻게 정하나요?

| 랭킹 | 기준 |
|---|---|
| 인기 FAQ | 최근 60분 동안 참고된 횟수가 많은 순 |
| 급상승 FAQ | 최근 60분의 참고 횟수가 직전 7일의 평균보다 많이 늘어난 순 |
| 지역별 급상승 FAQ | 해당 시·도의 기록만 사용해 급상승 순위 계산 |

#### 인기 FAQ

최근 60분에 20회 이상 참고된 FAQ 중 횟수가 많은 상위 5개를 보여줍니다.

#### 급상승 FAQ

직전 7일의 참고 횟수를 60분 평균으로 환산한 뒤, 최근 60분의 횟수와 비교합니다.

급상승 배율 = 최근 60분 참고 횟수 ÷ 과거 60분 평균 참고 횟수

예를 들어 직전 7일에 168회 참고됐다면 과거 60분 평균은 1회입니다. 최근 60분에 20회 참고됐다면 20배 급상승한 것입니다.

기본 설정에서는 최근 60분에 20회 이상, 직전 7일에 20회 이상 참고됐으며, 급상승 배율이 20배 이상인 FAQ만 후보가 됩니다. 과거 기록이 기준에 못 미치면 비교 대상에 포함되지 않습니다. 후보 중 배율이 높은 상위 5개를 보여줍니다.

#### 지역별 급상승 FAQ

질문을 받을 때 접속 IP로 시·도를 판별해 기록합니다. 지역별 순위는 최근 기록과 과거 기록 모두 같은 지역의 질문만 사용합니다. 지역을 판별할 수 없는 질문은 전국 랭킹에는 포함될 수 있지만 지역별 랭킹에서는 제외됩니다.

지역마다 별도의 최소 참고 횟수와 급상승 배율 기준을 설정할 수 있습니다. 별도 설정이 없으면 전국 랭킹과 같은 기본값을 사용합니다.

#### 언제 갱신하고 어떻게 조회하나요?

랭킹은 기본적으로 5분마다 다시 계산해 Redis에 저장합니다. GET /rankings는 저장된 인기·전국 급상승·지역별 급상승 결과를 한 번에 반환합니다. 각 결과에는 계산 시각도 포함되므로, 사용자가 조회한 시점과 실제 집계 시점을 구분할 수 있습니다.

## 4. 관리자 시스템

- FAQ·카테고리를 관리하고 변경 이력과 답변에 사용된 FAQ를 확인합니다.
- 미응답 질문을 검토해 새 FAQ로 등록합니다.
- 매장·상품·공지·장애 안내·방문 예약을 관리합니다.
- FAQ 이용 현황과 서비스 운영 지표를 확인하고, 금지어와 비회원 상담 횟수를 설정합니다.
<details>
<summary>미응답 질문은 어떻게 FAQ로 이어지나요?</summary>

---

#### 흐름

```text
사용자 질문
  └─ FAQ 검색에서 근거 없음(NO_FAQ) 또는 근거 부족(INSUFFICIENT_FAQ)
       └─ 질문을 임베딩해 미응답 질문으로 저장
            └─ 가장 가까운 미응답 묶음과 유사도 비교
                 ├─ 0.6 이상 → 기존 묶음에 합류 (묶음 중심 벡터·건수 다시 계산)
                 └─ 0.6 미만 → 새 묶음 생성
                      ↓
관리자가 묶음 목록 확인 (발생 횟수순·최신순, 상태 필터)
  └─ 묶음 상세에서 소속 질문 확인
       └─ 답변 입력 → FAQ 등록 (임베딩까지 한 번에)
            └─ 묶음 APPROVED + 등록한 FAQ 연결
                 ↓
같은 질문이 다시 들어오면 FAQ 검색을 통과
```

#### 규칙

| 규칙 | 내용 |
|---|---|
| 묶음 기준 | 유사도 0.6. bge-m3로 측정했을 때 같은 뜻 질문은 0.57~0.82, 관계없는 질문은 0.44~0.46 |
| 묶음 상태 | 대기(PENDING)·승인(APPROVED)·보류(ON_HOLD)·반려(REJECTED). 승인·반려된 묶음에는 새 질문이 합류하지 않음 |
| FAQ 등록 | 질문을 비우면 묶음의 대표 질문을 FAQ 질문으로 사용. 임베딩이 실패하면 FAQ 등록과 묶음 상태 변경을 함께 취소 |
| 동시 처리 | 관리자 두 명이 같은 묶음을 처리해도 묶음을 잠가 FAQ는 한 번만 등록 |
| 채팅 영향 | 미응답 저장이 실패해도 사용자 답변에는 영향 없음 |

#### FAQ 모니터링 수집 지표는 무엇이 있나요?

| 항목 | 확인할 수 있는 내용 |
|---|---|
| 미처리 질문 | 전체 질문 수, 처리 대기 중인 미응답 질문 수와 비율 |
| FAQ 사용량 | 많이 사용된 FAQ와 적게 사용된 FAQ |
| FAQ 유사도 | 사용자 질문과 참고 FAQ 사이의 평균 유사도가 높은 FAQ와 낮은 FAQ |

사용량과 유사도는 전체 FAQ와 질문 유형별로 나누어 집계합니다. 각 순위는 상위 20개와 하위 20개를 보여줍니다. 사용량은 답변에 참고된 횟수를 기준으로 하며, 한 답변에서 여러 FAQ를 참고했다면 각 FAQ의 사용량에 반영됩니다.

#### FAQ 하나를 자세히 볼 수 있나요?

FAQ를 선택하면 질문·답변·분류·버전과 함께 다음 지표를 확인할 수 있습니다.

| 지표 | 의미 |
|---|---|
| 사용량 추이 | 6시간·하루·한 달·1년 단위의 참고 횟수 변화 |
| 평균 유사도 | 사용자 질문과 이 FAQ 사이에 기록된 유사도의 평균 |
| 1순위 현황 | 이 FAQ가 검색 결과에서 1순위였던 횟수와 비율 |
| 1·2순위 차이 | 이 FAQ가 1순위일 때 2순위 FAQ와의 평균 유사도 차이 |
| 함께 등장한 FAQ | 같은 답변의 참고 목록에 자주 포함된 다른 FAQ |

사용량 추이에는 시점별 FAQ 버전도 표시해, FAQ를 수정한 전후의 변화를 살펴볼 수 있습니다.

#### 개선이 필요한 FAQ는 어떻게 찾나요?

시스템은 현재 FAQ 버전이 적용된 이후의 기록을 분석해 개선 후보를 표시합니다.

| 분류 | 기본 판단 기준 |
|---|---|
| 검색 품질 낮음 | 검색 상위 후보에 20회 이상 등장했지만 평균 유사도가 0.80 미만 |
| FAQ 중복 의심 | 1순위인 표본이 20회 이상이고, 1·2순위 유사도 차이가 0.05 미만인 경우가 30% 이상 |
| 사용도 낮음 | 현재 버전이 적용된 지 7일 이상 지났지만 최근 7일간 사용 기록이 없음 |

하나의 FAQ가 여러 분류에 동시에 해당할 수 있습니다. 관리자는 이 목록을 보고 내용을 보완하거나, 비슷한 FAQ를 검토하거나, 사용되지 않는 FAQ를 확인할 수 있습니다. 위 수치는 기본 설정이며 쌓인 데이터들을 바탕으로, 수치를 조절해가며 적정값을 선택할 예정입니다.

## 6. LLM

- FAQ 검색을 출발점으로 일반 상담(`GENERAL`), 사용자 정보 상담(`USER_DATA`), 매장 안내(`STORE_DATA`)를 연결합니다.
- 검색된 FAQ의 의도에 따라 참고할 FAQ, 조회할 사용자 정보, LLM에 제공할 매장 검색 도구를 준비합니다. 여러 의도의 자료가 필요하면 함께 모아 하나의 답변을 만듭니다.
- 일반 질문은 FAQ를 근거로 답하고, 내 정보 질문은 서버가 조회한 로그인 사용자 정보를 설명합니다.
- 매장 질문은 LLM의 도구 호출(Tool Calling)로 실제 주변 매장을 조회하고, 조회 결과를 답변과 지도용 데이터로 전달합니다. 현재 위치 좌표가 있으면 서버가 먼저 조회해 LLM에 결과를 제공합니다.
- 복합 질문은 하위 질문별로 검색하고, 이전 대화가 필요한 질문은 같은 대화의 최근 3턴까지 참고합니다.
- Qwen3-4B-Instruct-2507 계열 모델을 Ollama 또는 vLLM으로 연결하며, 답변 문장·근거 FAQ 번호·답변 상태를 구분한 JSON 형식을 사용합니다.

<summary>질문 의도에 따라 어떤 기능으로 연결되나요?</summary>

---

#### FAQ 검색에서 의도별 답변 준비까지

FAQ에는 관리자가 지정한 `GENERAL`·`USER_DATA`·`STORE_DATA` 라벨이 저장되어 있습니다. 사용자 질문과 유사한 FAQ를 검색한 뒤, 기준을 통과한 FAQ의 `intent`를 읽어 필요한 기능을 실행합니다.

Embedding 단계는 질문과 FAQ 표현을 벡터로 비교해 관련 FAQ를 찾는 역할입니다. 검색 결과의 의도 라벨을 받아 자료를 수집하고, 필요한 도구를 LLM에 제공해 답변으로 연결하는 단계가 아래 흐름입니다.

```text
사용자 질문 → 필요한 경우 질문 정리·맥락 보완
  └─ 임베딩으로 FAQ 검색 → 유사도 기준 판정
       └─ 검색된 FAQ의 intent별로 분기
            ├─ GENERAL    → FAQ 질문·답변을 참고 자료로 추가
            ├─ USER_DATA  → 로그인 사용자 정보를 서버에서 조회
            └─ STORE_DATA → 현재 위치 좌표 확인
                            ├─ 좌표 있음 → 서버가 주변 매장을 먼저 조회
                            └─ 좌표 없음 → LLM에 매장 검색 도구 제공
                                            └─ 도구 호출 요청
                                                 └─ 서버 조회 → 결과를 LLM에 전달
                 ↓
       원문 질문 + 의도별 자료 + 필요한 대화 이력으로 최종 답변 생성
```

#### 의도별 처리

| 의도 | 서버와 LLM의 역할 | LLM이 받는 자료 |
|---|---|---|
| `GENERAL` | 검색된 FAQ를 근거로 질문에 맞는 설명 생성 | FAQ의 질문·답변 |
| `USER_DATA` | 서버가 로그인 사용자 정보를 조회하고, LLM이 조회 내용을 설명 | 사용자 정보 섹션. 조회할 수 없으면 그 상태를 전달 |
| `STORE_DATA` | 현재 위치로 먼저 조회하거나, LLM의 매장 검색 도구 호출을 실행해 결과 전달 | 실제 매장 조회 결과 또는 호출 가능한 매장 검색 도구 |

현재 사용자 정보 상담에 전달하는 항목은 이름·거주 지역·가입일입니다. 사용자 페이지에서 제공하는 다른 조회 기능과 별개로, 이 상담 경로에는 요금·데이터 사용량·미납 정보를 전달하지 않습니다. 비회원이거나 사용자 정보를 찾지 못하면 조회할 수 없다는 자료를 넣습니다.

한 번의 검색에서 여러 의도의 FAQ가 잡히면 해당 의도의 핸들러를 각각 실행합니다. 복합 질문의 여러 하위 질문에서 같은 의도가 반복되어도 핸들러는 의도마다 한 번만 실행해 자료를 모읍니다.

#### 의도가 다르게 연결됐을 때

로그인 사용자는 성공한 답변에서 일반·매장·내 정보 중 의도를 직접 골라 같은 의도당 한 번 다시 검색할 수 있습니다. 재검색은 고른 의도의 FAQ만 대상으로 하며, 이후 해당 의도의 자료·도구를 준비해 답변합니다. 자세한 규칙은 AI 챗봇 서비스의 “의도별 재검색” 항목을 따릅니다.

#### LLM의 호출 요청과 서버의 실행

매장 의도의 FAQ가 검색되고 현재 위치 좌표가 없으면, 서버는 `findNearbyStores` 도구의 설명과 입력 형식을 LLM에 제공합니다. LLM이 장소명을 담은 호출을 요청하면 서버가 실제 조회를 실행하고, 그 결과를 도구 응답으로 돌려줍니다. LLM은 이 결과를 받아 최종 안내 문장을 만듭니다.

```text
“강남역 근처 매장 찾아줘”
  └─ STORE_DATA 의도의 FAQ 검색
       └─ 매장 검색 도구를 포함한 LLM 요청
            └─ LLM: findNearbyStores(place="강남역") 호출 요청
                 └─ 서버: 질문 맥락에 있는 장소인지 검사
                      └─ 카카오 장소 검색으로 기준 좌표 확인
                           └─ 매장 DB에서 주변 매장 조회
                                ├─ 조회 결과 → 도구 응답 → LLM의 최종 안내
                                └─ 같은 매장 목록 → 지도용 데이터
```

도구 조회 기본 범위는 반경 3km, 가까운 순 최대 5곳입니다. 매장 이름·주소·전화번호·영업시간·거리를 조회하며, 실제 조회된 목록은 답변 문장과 별도로 화면에 전달합니다.

#### 장소명과 현재 위치에 따른 처리

| 상황 | 처리 |
|---|---|
| 장소명을 말하고 현재 위치 좌표는 보내지 않음 | LLM이 장소명을 도구 인자로 요청하고 서버가 좌표를 찾아 조회 |
| “내 근처 매장”처럼 기준 장소·좌표가 없음 | 도구가 위치 필요 상태(`locationRequired`)를 기록해 화면에 전달 |
| 화면이 현재 위치 좌표와 함께 요청 | 서버가 해당 좌표로 먼저 매장을 조회하고, LLM은 조회 결과를 설명 |
| 장소를 찾지 못함 | 찾지 못했다는 도구 결과를 전달해 정확한 지명을 안내하도록 함 |
| 주변 매장이 없음 | 빈 목록과 검색 범위를 전달해 해당 범위에 매장이 없다고 안내 |
| 외부 장소 검색·매장 조회 실패 | 조회 실패 결과를 전달해 실제 매장 정보를 추측하지 않도록 함 |

LLM이 도구에 넣는 장소명은 전달된 질문 맥락과 대조합니다. 질문 맥락에 없는 장소를 넣거나 철자를 임의로 바꾸면 다시 호출하도록 결과를 돌려줍니다. 장소 좌표와 매장 목록은 서버의 실제 조회로 정합니다.

#### 도구 실행과 최종 응답

Ollama는 Spring AI의 도구 실행 흐름을 사용하고, vLLM 연결은 OpenAI 호환 `tool_calls` 요청과 `tool` 응답으로 실행 결과를 주고받습니다. 도구 실행 결과를 받은 뒤 최종 답변이 완성될 때까지 모델 호출이 이어질 수 있습니다.

매장 도구가 붙은 요청은 도구 호출을 허용하기 위해 JSON Schema 강제를 제외합니다. 최종 답변 형식은 프롬프트로 요구하고, 매장 목록은 서버가 별도로 기록해 지도와 연결합니다.

#### 질문 정리와 답변 생성

LLM의 역할을 질문 정리와 최종 답변 생성으로 나눕니다. 질문 정리 LLM은 검색할 질문을 만들고, 답변 LLM은 사용자 원문과 검색된 근거를 받아 상담 답변을 만듭니다.

```text
사용자 질문
  └─ 코드로 질문 분리·이전 대화 참조 표지 확인
       ├─ 표지 없음 → 원문으로 FAQ 검색
       │               ├─ 유사도 기준 통과 → 질문 정리 생략
       │               └─ 기준 미달 → 질문 정리 LLM
       └─ 표지 있음 → 질문 정리 LLM
                         └─ 이전 대화의 맥락 보완 + 하위 질문 분리
                              └─ 검색어 변형 검사·보정
                                   ↓
                         하위 질문마다 FAQ 검색
                                   ↓
                         사용자 원문 + 의도별 자료·도구 준비
                                   ↓
                         필요한 경우에만 이전 대화 첨부
                                   ↓
                         하나의 상담 답변 생성
```

질문 정리 LLM은 한 턴에 최대 한 번 호출합니다. 원문 검색으로 충분한 질문은 이 호출을 생략합니다. 원문 검색만으로 진행할 기본 기준은 이전 대화가 없으면 0.75, 있으면 0.80입니다.

#### 질문을 나누는 기준

| 상황 | 처리 |
|---|---|
| “유심 재발급 방법이랑 해외 로밍 요금 알려줘” | 독립된 질문으로 나누어 각각 검색 |
| “그거 온라인으로도 돼요?” | 앞선 대화에서 가리키는 대상을 찾아 검색어에 보완 |
| “A와 B의 차이가 뭐예요?”처럼 하나의 비교를 묻는 질문 | 프롬프트에서 한 질문으로 유지하도록 지시 |
| 하위 질문이 4개 이상 | 한 번에 처리하는 최대 3개를 넘으므로 질문을 나누어 달라는 안내로 종료 |
| 질문 정리 호출·응답 해석 실패 | 원문 질문 하나로 검색을 계속 진행 |

한국어 형태소 분석과 문장 패턴으로 나열·연결 표현, 지시어, 생략형 질문 등을 확인합니다. 지시어와 이어 묻기 같은 멀티턴 표지는 이전 대화가 있을 때만 판단합니다.

#### 검색어와 원문을 구분하는 이유

질문 정리 과정에서 부정이 뒤집히거나 숫자·고유명사가 바뀌는 사례가 있었습니다. 이를 줄이기 위해 다시 쓴 문장은 FAQ 검색에만 사용하고, 답변 LLM에는 사용자가 입력한 원문을 전달합니다.

질문이 여러 개면 코드가 원문을 조각으로 나누고, 참고 자료로 채택한 GENERAL FAQ를 해당 조각 아래에 묶습니다. 원문을 나누지 못하면 각 묶음의 제목에 원문 전체를 사용합니다.

| 검색어 검사 | 처리 |
|---|---|
| 봇에게 내린 명령이 검색 질문으로 바뀜 | 해당 검색어 제외 |
| 부정 변경·질문 대신 답변 작성·프롬프트 문구 혼입 | 해당 부분을 원문 조각으로 검색 |
| 복구 가능한 숫자·고유명사 철자 변경 | 원문 표기로 보정 |
| 원문·이전 대화에 없는 외국 문자 혼입 | 해당 문자 제거 |

#### 이전 대화 사용

- 같은 대화에서 현재 질문보다 앞선 최근 3턴을 가져오며, 재시도는 처음 질문했을 때의 이전 대화를 기준으로 합니다.
- 질문 정리 LLM을 부를 때는 이전 대화가 있으면 함께 전달해 생략된 대상과 조건을 보완합니다.
- 최종 답변 LLM에는 멀티턴으로 판단한 경우에만 이전 대화를 user·assistant 메시지로 전달합니다. 독립된 질문에 이전 답변의 잘못된 정보가 섞이는 것을 줄이기 위한 방식입니다.
- 실패한 턴은 답변을 만들어 넣지 않고 `(답변 실패)`로 표시합니다.
- 의도별 재검색은 질문 정리 LLM을 다시 호출하지 않고 원본 시도의 하위 질문을 재사용합니다.

로컬 질문 분리 실험 100건에서는 올바르게 나눈 질문이 기존 81건에서 현재 프롬프트 90건으로 늘었습니다. AI가 만든 질문과 기대값을 사용한 단회 평가이며, 사람 검수 전 결과입니다. 전체 상담 정답률이나 멀티턴 정답률을 뜻하지 않습니다.

#### 검색 기준과 답변 자료

하위 질문마다 코사인 유사도 기준을 통과한 FAQ를 기본 최대 3개까지 선택해 의도별 처리에 사용합니다. 재정렬(Reranker)을 켜면 후보의 순서를 다시 정하지만, 근거로 채택할지는 코사인 유사도 기준으로 판단합니다.

최종 답변에는 GENERAL FAQ 원문, 서버가 조회한 사용자 정보, 매장 도구의 실제 결과를 각 경로에 맞춰 전달합니다. 도구나 자료로 확인한 범위에서 설명하고, 실행하지 않은 업무를 처리했다고 답하지 않도록 프롬프트에서 제한합니다.

#### 일부 질문만 답할 수 있을 때

- 하위 질문 일부에만 FAQ가 있으면, 확인된 내용은 답하고 근거가 없는 부분은 확인할 수 없다고 안내하도록 지시합니다.
- 모든 하위 질문에 근거가 없으면 최종 답변 LLM을 호출하지 않고 미응답으로 처리합니다.
- 근거를 찾지 못한 하위 질문은 따로 미응답 질문으로 기록해 FAQ 보완에 활용합니다. 사용자가 의도를 직접 고른 재검색은 이 기록에서 제외합니다.

#### 공식 FAQ를 바로 반환하는 경로

`develop`에는 공식 FAQ 답변을 직접 반환하는 시맨틱 캐시 경로도 있습니다. 이 기능을 켜고, 캐시가 허용된 일반 FAQ의 1순위 유사도와 2순위와의 점수 차이가 기준을 모두 통과하면 등록된 공식 답변을 반환합니다.

기본 설정은 비활성화이며, 기준 기본값은 유사도 0.95 이상·점수 차이 0.15 이상입니다. 매장·내 정보처럼 별도 맥락이 필요한 의도는 제외하고, 캐시 조건을 통과하지 않으면 검색된 후보로 LLM 답변 생성을 이어갑니다.

답변 생성 작업은 `develop`의 비동기 Worker에서 처리하고, 화면은 작업 번호로 상태와 최종 결과를 조회합니다.

#### 프롬프트 관리

질문 정리와 답변 생성 지침을 각각 시스템 지침·사용자 템플릿 파일로 관리합니다.

| 역할 | 파일 | 핵심 내용 |
|---|---|---|
| 질문 정리 | `sub-question-system.txt` · `sub-question-user.txt` | 대화 맥락 보완, 하위 질문 분리, 검색용 표현 생성 |
| 최종 답변 | `faq-system.txt` · `faq-user.txt` | FAQ·추가 자료에 근거한 답변, 근거 부족·충돌·범위 밖 상황 처리 |

최종 답변 프롬프트는 LLM 테스트 저장소의 `v5_i4b`를 백엔드에 적용한 버전입니다. 매장 조회 도구와 FAQ 번호 표기처럼 백엔드 입력에 필요한 부분을 맞춰 사용합니다.

튜닝 7차의 `v5_i4`는 같은 900건 비교에서 정답 703 → 698건, 환각이 포함된 답변 184 → 122건, 되묻기 126 → 1건이었습니다. 정답률을 유지하면서 환각과 불필요한 되묻기를 줄이는 방향으로 조정했지만, 범위 밖 질문의 정답은 94 → 82건으로 낮아졌습니다. 이후 범위 밖 안내 문장 하나를 뺀 `v5_i4b` 자체는 같은 조건으로 전수 평가하지 않았으므로 이 수치를 현재 프롬프트의 측정값으로 보지는 않습니다.

#### 구조화 출력

일반 답변 생성에는 JSON Schema를 함께 전달해 다음 형식을 요구합니다.

| 필드 | 역할 |
|---|---|
| `answer` | 사용자에게 전달할 한국어 답변 |
| `evidence_ids` | 모델이 답변 근거로 선택한 FAQ ID 목록 |
| `status` | `ANSWER` · `PARTIAL` · `ABSTAIN` · `CONFLICT` · `OUT_OF_SCOPE` |

Ollama는 `format`, vLLM은 `response_format`으로 스키마를 전달합니다. 매장 조회 도구가 붙은 요청은 도구 호출을 허용하기 위해 스키마 강제를 제외하고 프롬프트로 형식을 요구합니다.

서버는 출력에서 `answer`를 꺼내 화면에 전달합니다. JSON처럼 보이지만 해석할 수 없거나 답변 문장이 비어 있으면 생성 실패로 처리합니다. 도구 경로처럼 스키마를 강제하지 않은 요청을 위해 일반 문장 응답도 처리합니다.

현재 `status`와 `evidence_ids`는 모델 출력 확인용 로그에 남습니다. 채팅의 성공·실패 상태는 서버가 별도로 관리하고, 참고 FAQ 이력에는 모델이 선택한 ID와 별개로 전달한 FAQ를 기록합니다.

## 7. Embedding

이 프로젝트에서 벡터 임베딩은 다음과 같이 사용하고 있습니다.

사용자 질문과 FAQ 질문을 벡터로 변환해, 표현이 달라도 의미가 비슷한 FAQ를 찾습니다. FAQ의 원본 질문뿐 아니라 유사 질문도 검색 대상에 포함합니다.

검색된 FAQ의 답변에서 사용자 질문과 관련 있는 문장을 다시 골라 LLM에 전달합니다. 조건을 충족하는 FAQ는 LLM을 거치지 않고 등록된 답변을 바로 제공합니다.

답변할 FAQ를 찾지 못한 질문은 임베딩 유사도로 묶습니다. 관리자는 반복되는 미응답 질문을 확인하고 새 FAQ를 만드는 데 활용할 수 있습니다.

Ollama와 vLLM 임베딩 서버를 지원하며, 모델별 벡터를 분리해 저장합니다. 모델을 변경했을 때는 기존 FAQ와 미응답 질문의 벡터를 새 모델로 채울 수 있습니다.

현재 모델은 BGE-M3를 사용하고 있습니다.

## 1. 유플러스 챗봇을 직접 사용해보니, 장소 관련 질문을 하면 챗봇에서 직접 해당 장소를 안내해주는게 아니라 매장 찾기 페이지로 연결을 해줍니다. 다른 회사의 챗봇 서비스들도 비슷하게 작동하는데, 혹시 이렇게 구현하는 이유가 있을까요?

- 현업에서는 이미 구축된 기능을 배제할 필요가 없다는 의견
- 챗봇 내부에 지도 표시 기능을 새로 추가하기보다, 기존 매장 안내 기능을 활용하는 편이 개발 측면에서 더 용이할 수 있다는 설명

## 2. 실제 AI 상담 서비스를 운영할 때, 사용자의 질문이 명확하지 않아 답변을 어떻게 해야하는지 모르는 경우가 많을 것 같습니다. 이런 경우 질문을 하냐 마냐 경계를 정하는 기준이 있을것 같은데, 현업에서는 LLM이 어떻게 기준을 정하게 하는지 궁금합니다.

- 모든 서비스에 공통으로 적용되는 단일 기준값이나 정답의 부재
- 기획 단계에서 서비스별 시나리오와 예외 처리 원칙을 정의하는 방식
- 특정 서비스 예시: 로밍 서비스
    - 사용자가 할 법한 질문과 대화 시나리오의 사전 정리
    - 시나리오별 필요 업무 API 준비
    - AI 검색·LLM의 요청 시나리오 분기
    - 업무 시스템의 API 기반 처리
- 준비된 시나리오 밖의 질문 또는 유사도 기반 답변이 어려운 질문에 대한 사전 정책 필요
    - 일정 유사도 이상일 때 답변 여부
    - 조건에 맞는 답변이 없을 때 상담 연결 여부
