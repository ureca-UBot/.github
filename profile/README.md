## 1. 유플러스 챗봇을 직접 사용해보니, 장소 관련 질문을 하면 챗봇에서 직접 해당 장소를 안내해주는게 아니라 매장 찾기 페이지로 연결을 해줍니다. 다른 회사의 챗봇 서비스들도 비슷하게 작동하는데, 혹시 이렇게 구현하는 이유가 있을까요?

- 현업에서는 이미 구축된 기능을 배제할 필요가 없다는 의견
- 챗봇 내부에 지도 표시 기능을 새로 추가하기보다, 기존 매장 안내 기능을 활용하는 편이 개발 측면에서 더 용이할 수 있다는 설명

## 2. 실제 AI 상담 서비스를 운영할 때, 사용자의 질문이 명확하지 않아 답변을 어떻게 해야하는지 모르는 경우가 많을 것 같습니다. 이런 경우 질문을 하냐 마냐 경계를 정하는 기준이 있을것 같은데, 현업에서는 LLM이 어떻게 기준을 정하게 하는지 궁금합니다.

- 모든 서비스에 공통으로 적용되는 단일 기준값이나 정답의 부재
- 기획 단계에서 서비스별 시나리오와 예외 처리 원칙을 정의하는 방식
- 특정 서비스 예시: 로밍 서비스
    - 사용자가 할 법한 질문과 대화 시나리오의 사전 정리
    - 시나리오별 필요 업무 API 준비
    - AI 검색·LLM의 요청 시나리오 분기
    - 업무 시스템의 API 기반 처리
- 준비된 시나리오 밖의 질문 또는 유사도 기반 답변이 어려운 질문에 대한 사전 정책 필요
    - 일정 유사도 이상일 때 답변 여부
    - 조건에 맞는 답변이 없을 때 상담 연결 여부
    - 고객 안내 문구
- 프로젝트 차원의 답변·상담 연결·미답변 처리 기준 명문화 필요성 강조

## 3. 저희가 만든 임베딩 모델의 유사도 threshold를 실험으로 정하고 있는데, 실무에서는 threshold를 어떤 기준으로 정하고, 추후에 변경한다면, 어떤 이유에 근거해서 변경하는지 궁금합니다.

- 유사도가 높더라도 정답을 보장하지는 않는다는 점
- 테스트 결과 기반의 Threshold 설정 필요
- 정답·오답 사례 검증을 통한 적정 임계값 도출
- Threshold 선정 근거의 명확화 필요
    - 실험 방식
    - 실험 결과
    - 해당 임계값을 선택한 이유
- Threshold 변경 시에도 성능 측정 결과와 운영상 오류 사례를 근거로 한 변경 사유 제시 필요

## 4. 임베딩 방법중에, Dense, Sparse, Multi-vector 세개가 있다고 알고 있습니다. 실무에서는 성능 개선을 위해 가벼운 파트에는 Dense만, 복잡한 파트에는 여러 방법을 섞은 hybrid방식을 사용할 것 같은데, 가벼운 파트와 무거운 파트를 어떤 기준으로 구분하는지 궁금합니다.

- AI 검색·LLM 기반 검색 구현 경험 부족으로, 가벼운 작업과 복잡한 작업을 나누는 구체적인 실무 기준에 대한 답변 한계
- 다른 팀의 요청 특성별 모델 오케스트레이션 준비 사례 언급
    - 단순 요청: 경량 모델 사용
    - 높은 수준의 추론 필요 요청: 고성능 모델 사용
- 모델·서버 비용의 경우, 기능 필요성과 성능 검증 자료를 근거로 비용 부서와 협의 및 승인 진행

## 6. 저희는 미답변 로그를 클러스터링해서 신규 FAQ 후보를 발굴하려고 하는데, 실무에서 이런 '콘텐츠 갭 발견' 파이프라인을 실제로 운영해보신 경험이 있으신가요?

- 미답변 로그 클러스터링을 통한 신규 FAQ 후보 발굴 경험 부재
- 기능 자체에 대한 긍정적 평가와 운영 모니터링 체계의 중요성 강조
- 유사 사례: 고객 참여형 서비스의 댓글 운영
    - 욕설·무관한 내용·부적절한 표현 사전 필터링
    - 신고 콘텐츠 또는 특정 조건 콘텐츠에 대한 운영자 알림
    - 운영자 검토 및 조치를 위한 관리 장치 마련
- 미답변 질문 관리 적용 방향
    - 미답변 질문 목록화
    - 관리자 검토
    - 확인된 질문의 FAQ DB 추가
    - 처리 완료·미완료 상태 관리
- 실서비스 운영 측면의 유용성 언급

## 7. 임베딩 모델을 추가 데이터로 파인튜닝해본 경험이 있으신가요? 사전학습 모델 그대로 쓰는 것과 비교해서 실제로 유의미한 개선이 있었나요?

- 내부 임베딩 모델 추가 학습·파인튜닝 사례에 대한 인지 부족
- 사전학습 모델 대비 파인튜닝 효과의 정량적 비교 사례 부재
- 실무의 주요 제약 요인으로서 보안 이슈 언급
    - AI 활용 시 보안팀 검토 필요
    - 외부 모델 대신 로컬 환경 활용 방식 준비
    - 요청 특성별 경량 모델·고성능 모델 선택 오케스트레이션 검토

## 8. LLM 모델 평가 지표를 확정하기 어려웠습니다. 한국어를 지원하는 모듈도 많지 않았고 정확도가 다소 떨어진다고 판단했습니다. LLM이나 인간이 JUDGE 하지 않고, 한국어 능력이나 정보의 정확도를 정확하게 따질 수 있는 테스트 기준을 찾기 어려웠습니다. 실무에서는 LLM 성능을 어떻게 평가하는지 궁금합니다.

- LLM 평가 전문 경험 부족
- 프로젝트 목적에 맞는 평가 기준과 수치의 직접 정의·검증 방식 제안
- 업무 담당자가 실제 요구사항과 정답을 알고 있을 때 가능한 판단
    - LLM 답변의 업무 적절성
    - 예상 답변·처리 결과 충족 여부
- 권장 평가 방식
    - 질문과 정답이 정해진 테스트셋 준비
    - 답변 정확도 측정
    - 기대 답변과의 유사성 측정
    - 미답변·오답 여부 측정
- 회사 내부 환경
    - 보안상 사용 가능 LLM의 사전 제한
    - 여러 모델 간 비교보다 허용 모델의 로직 수행 및 예상 결과 충족 여부 중심 평가

# 프로젝트 차별점에 대한 의견

## 긍정적으로 평가한 요소

### 자주 묻는 질문·연관 질문 추천

- 사용자의 첫 질문에 관련 질문을 함께 제시하는 기능의 유용성
- 벡터 검색 또는 키워드 기반 구현 가능성 언급

### 미응답 질문 관리

- 가장 구체적으로 긍정 평가한 운영 기능
- 관리자 페이지 기반의 미응답 질문 목록화·검토·FAQ 반영·처리 상태 관리
- 실서비스 운영 측면의 높은 활용 가능성

### AI 챗봇과 실제 서비스 연결

- 매장 안내, 매장 예약, 상담 가능 시간 안내, 예약 신청 알림 등 실제 서비스 흐름 연결 방안에 대한 긍정적 의견
- 단순 정보 제공을 넘어 업무·예약 흐름까지 처리하는 기능의 차별화 가능성

### 지역·주제별 이상 징후 감지

- 특정 지역에서 동일·유사 문의가 급증할 때 지도에 표시하고 담당자에게 알리는 기능의 긍정적 평가
- 특정 지역의 장애 문의 급증 시 네트워크·송신탑 이슈 가능성을 담당자에게 전달하는 방식
- 지역 단위뿐 아니라 전국 단위의 급증 패턴 감지 및 관리자 알림 가능성

## 향후 확장 아이디어

- 벡터 DB 중심 RAG 구조와 그래프 DB의 결합 가능성 제안
- 활용 예시
    - 특정 상품 구매자의 추가 구매 상품
    - 동일 상품 구매자의 빈번한 질문
    - 상품·고객·질문 간 관계 기반 추천
- 2차 MVP 이후의 확장 방향으로 검토 권장

## 구현 시 유의할 점: 개인정보·보안

- 사용자 TV 정보 등 개인정보를 API로 조회해 답변에 활용하는 경우 개인정보보호팀·정보보호팀 검토 필요
- 오픈 전 확인 항목
    - 개인정보 처리·암호화 방식
    - 사용자 세션에 맞는 정보만 조회·전달되는지 여부
    - 타 사용자 정보 노출 방지를 위한 서버 측 검증
- 개인화 답변 기능의 차별화 가능성과 서비스화 단계의 보안 검토 필수성 강조
