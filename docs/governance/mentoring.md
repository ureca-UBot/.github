### 1. 유플러스 챗봇을 직접 사용해보니, 장소 관련 질문을 하면 챗봇에서 직접 해당 장소를 안내해주는게 아니라 매장 찾기 페이지로 연결을 해줍니다. 다른 회사의 챗봇 서비스들도 비슷하게 작동하는데, 혹시 이렇게 구현하는 이유가 있을까요?

- 현업에서는 이미 구축된 기능을 배제할 필요가 없다는 의견
- 챗봇 내부에 지도 표시 기능을 새로 추가하기보다, 기존 매장 안내 기능을 활용하는 편이 개발 측면에서 더 용이할 수 있다는 설명

### 2. 실제 AI 상담 서비스를 운영할 때, 사용자의 질문이 명확하지 않아 답변을 어떻게 해야하는지 모르는 경우가 많을 것 같습니다. 이런 경우 질문을 하냐 마냐 경계를 정하는 기준이 있을것 같은데, 현업에서는 LLM이 어떻게 기준을 정하게 하는지 궁금합니다.

- 모든 서비스에 공통으로 적용되는 단일 기준값이나 정답의 부재
- 기획 단계에서 서비스별 시나리오와 예외 처리 원칙을 정의하는 방식
- 특정 서비스 예시: 로밍 서비스
    - 사용자가 할 법한 질문과 대화 시나리오의 사전 정리
    - 시나리오별 필요 업무 API 준비
    - AI 검색·LLM의 요청 시나리오 분기
    - 업무 시스템의 API 기반 처리
- 준비된 시나리오 밖의 질문 또는 유사도 기반 답변이 어려운 질문에 대한 사전 정책 필요
    - 일정 유사도 이상일 때 답변 여부
    - 조건에 맞는 답변이 없을 때 상담 연결 여부
    - 고객 안내 문구
- 프로젝트 차원의 답변·상담 연결·미답변 처리 기준 명문화 필요성 강조

### 3. 저희가 만든 임베딩 모델의 유사도 threshold를 실험으로 정하고 있는데, 실무에서는 threshold를 어떤 기준으로 정하고, 추후에 변경한다면, 어떤 이유에 근거해서 변경하는지 궁금합니다.

- 유사도가 높더라도 정답을 보장하지는 않는다는 점
- 테스트 결과 기반의 Threshold 설정 필요
- 정답·오답 사례 검증을 통한 적정 임계값 도출
- Threshold 선정 근거의 명확화 필요
    - 실험 방식
    - 실험 결과
    - 해당 임계값을 선택한 이유
- Threshold 변경 시에도 성능 측정 결과와 운영상 오류 사례를 근거로 한 변경 사유 제시 필요

### 4. 임베딩 방법중에, Dense, Sparse, Multi-vector 세개가 있다고 알고 있습니다. 실무에서는 성능 개선을 위해 가벼운 파트에는 Dense만, 복잡한 파트에는 여러 방법을 섞은 hybrid방식을 사용할 것 같은데, 가벼운 파트와 무거운 파트를 어떤 기준으로 구분하는지 궁금합니다.

- AI 검색·LLM 기반 검색 구현 경험 부족으로, 가벼운 작업과 복잡한 작업을 나누는 구체적인 실무 기준에 대한 답변 한계
- 다른 팀의 요청 특성별 모델 오케스트레이션 준비 사례 언급
    - 단순 요청: 경량 모델 사용
    - 높은 수준의 추론 필요 요청: 고성능 모델 사용
- 모델·서버 비용의 경우, 기능 필요성과 성능 검증 자료를 근거로 비용 부서와 협의 및 승인 진행

### 6. 저희는 미답변 로그를 클러스터링해서 신규 FAQ 후보를 발굴하려고 하는데, 실무에서 이런 '콘텐츠 갭 발견' 파이프라인을 실제로 운영해보신 경험이 있으신가요?

- 미답변 로그 클러스터링을 통한 신규 FAQ 후보 발굴 경험 부재
- 기능 자체에 대한 긍정적 평가와 운영 모니터링 체계의 중요성 강조
- 유사 사례: 고객 참여형 서비스의 댓글 운영
    - 욕설·무관한 내용·부적절한 표현 사전 필터링
    - 신고 콘텐츠 또는 특정 조건 콘텐츠에 대한 운영자 알림
    - 운영자 검토 및 조치를 위한 관리 장치 마련
- 미답변 질문 관리 적용 방향
    - 미답변 질문 목록화
    - 관리자 검토
    - 확인된 질문의 FAQ DB 추가
    - 처리 완료·미완료 상태 관리
- 실서비스 운영 측면의 유용성 언급

### 7. 임베딩 모델을 추가 데이터로 파인튜닝해본 경험이 있으신가요? 사전학습 모델 그대로 쓰는 것과 비교해서 실제로 유의미한 개선이 있었나요?

- 내부 임베딩 모델 추가 학습·파인튜닝 사례에 대한 인지 부족
- 사전학습 모델 대비 파인튜닝 효과의 정량적 비교 사례 부재
- 실무의 주요 제약 요인으로서 보안 이슈 언급
    - AI 활용 시 보안팀 검토 필요
    - 외부 모델 대신 로컬 환경 활용 방식 준비
    - 요청 특성별 경량 모델·고성능 모델 선택 오케스트레이션 검토

### 8. LLM 모델 평가 지표를 확정하기 어려웠습니다. 한국어를 지원하는 모듈도 많지 않았고 정확도가 다소 떨어진다고 판단했습니다. LLM이나 인간이 JUDGE 하지 않고, 한국어 능력이나 정보의 정확도를 정확하게 따질 수 있는 테스트 기준을 찾기 어려웠습니다. 실무에서는 LLM 성능을 어떻게 평가하는지 궁금합니다.

- LLM 평가 전문 경험 부족
- 프로젝트 목적에 맞는 평가 기준과 수치의 직접 정의·검증 방식 제안
- 업무 담당자가 실제 요구사항과 정답을 알고 있을 때 가능한 판단
    - LLM 답변의 업무 적절성
    - 예상 답변·처리 결과 충족 여부
- 권장 평가 방식
    - 질문과 정답이 정해진 테스트셋 준비
    - 답변 정확도 측정
    - 기대 답변과의 유사성 측정
    - 미답변·오답 여부 측정
- 회사 내부 환경
    - 보안상 사용 가능 LLM의 사전 제한
    - 여러 모델 간 비교보다 허용 모델의 로직 수행 및 예상 결과 충족 여부 중심 평가

### 프로젝트 차별점에 대한 의견

#### 긍정적으로 평가한 요소

##### 자주 묻는 질문·연관 질문 추천

- 사용자의 첫 질문에 관련 질문을 함께 제시하는 기능의 유용성
- 벡터 검색 또는 키워드 기반 구현 가능성 언급

##### 미응답 질문 관리

- 가장 구체적으로 긍정 평가한 운영 기능
- 관리자 페이지 기반의 미응답 질문 목록화·검토·FAQ 반영·처리 상태 관리
- 실서비스 운영 측면의 높은 활용 가능성

##### AI 챗봇과 실제 서비스 연결

- 매장 안내, 매장 예약, 상담 가능 시간 안내, 예약 신청 알림 등 실제 서비스 흐름 연결 방안에 대한 긍정적 의견
- 단순 정보 제공을 넘어 업무·예약 흐름까지 처리하는 기능의 차별화 가능성

##### 지역·주제별 이상 징후 감지

- 특정 지역에서 동일·유사 문의가 급증할 때 지도에 표시하고 담당자에게 알리는 기능의 긍정적 평가
- 특정 지역의 장애 문의 급증 시 네트워크·송신탑 이슈 가능성을 담당자에게 전달하는 방식
- 지역 단위뿐 아니라 전국 단위의 급증 패턴 감지 및 관리자 알림 가능성

#### 향후 확장 아이디어

- 벡터 DB 중심 RAG 구조와 그래프 DB의 결합 가능성 제안
- 활용 예시
    - 특정 상품 구매자의 추가 구매 상품
    - 동일 상품 구매자의 빈번한 질문
    - 상품·고객·질문 간 관계 기반 추천
- 2차 MVP 이후의 확장 방향으로 검토 권장

#### 구현 시 유의할 점: 개인정보·보안

- 사용자 TV 정보 등 개인정보를 API로 조회해 답변에 활용하는 경우 개인정보보호팀·정보보호팀 검토 필요
- 오픈 전 확인 항목
    - 개인정보 처리·암호화 방식
    - 사용자 세션에 맞는 정보만 조회·전달되는지 여부
    - 타 사용자 정보 노출 방지를 위한 서버 측 검증
- 개인화 답변 기능의 차별화 가능성과 서비스화 단계의 보안 검토 필수성 강조

## 2차 멘토링 질문

  <summary>열기 / 닫기</summary>

### Transaction / HikariCP / DB Connection

1. 처리 이력이나 로그 저장에 `REQUIRES_NEW` 같은 별도 Transaction을 사용하는 패턴을 실무에서 사용해보셨나요? 주의할 점이 있나요?
2. 외부 API 호출 전후에 DB 작업이 있다면, 외부 API를 기다리는 동안 Transaction이나 Connection을 잡지 않는 구조가 일반적으로 더 좋은가요?

### 비동기 처리 / Thread / Concurrency

1. 서버는 요청을 계속 받을 수 있는데 뒤쪽 서비스의 처리량이 낮다면 Queue에 대기시키는 것과 빠르게 실패시키는 것 중 어떻게 선택하시나요?
2. 동시 요청을 제한할 때 Semaphore, Thread Pool 크기, Queue 크기 중 어떤 계층에서 제어하는 방식을 주로 사용하셨나요?

### Timeout / Retry / Idempotency

1. 재시도 가능한 API를 설계할 때 Idempotency Key를 실제로 사용해보셨다면 어느 계층에서 검증하는 게 좋나요?

### Scheduler / Batch

1. Scheduler를 운영해보셨을 때 가장 자주 발생했던 문제는 무엇인가요?
2. Scheduler가 여러 서버 인스턴스에서 동시에 실행되는 문제는 실무에서 어떻게 막으셨나요?

### 부하 테스트 / 성능 병목

1. 부하 테스트를 처음 설계할 때 목표 동시 사용자 수는 어떤 근거로 결정하시나요?

### Monitoring / 운영

1. 실제 운영 시스템을 모니터링할 때 반드시 확인하는 지표를 5개만 고른다면 어떤 것을 보시나요?
2. 모니터링 지표가 너무 많아지는 것을 막기 위해 어떤 기준으로 지표를 선택하시나요?

### API / 서비스 설계

1. API 응답은 실패했지만 내부 처리는 성공한 부분 실패 상황을 실무에서는 어떻게 표현하고 관리하셨나요?

### 아키텍처 / MVP 범위 판단

1. 저희 현재 구조를 보셨을 때 앞으로 가장 먼저 문제가 생길 가능성이 높은 부분이 어디라고 보시나요?
2. 기능 구조가 계속 바뀌는 프로젝트에서 공통 인프라를 어느 시점에 넣는 게 적절한가요?

### 레거시 / 변경 관리 / 점진적 개선

1. 기술 부채를 “지금 고쳐야 할 것”과 “나중에 고쳐도 되는 것”으로 어떻게 분류하시나요?

### 경험 정리와 업무 분담

1. 프로젝트를 진행하고 나면, 포트폴리오든, 자소서에 쓸 경험이든 정리를 해야할텐데 혹시 본인만의 노하우가 있는지 궁금합니다. 결국 회사에서 원하는건, 문제가 생겼을때 어떻게 해결하는지를 볼 것 같은데… 아무래도 AI를 많이 활용하다보니까, 구조도 같이 짜주고, 내가 생각한 구조를 평가해달라고 하면 전혀 생각지도 못했던 문제 혹은 개선안을 먼저 말해줘서, 트러블슈팅할 일이 사실 그렇게 많지가 않았습니다. 프로젝트를 진행하면서, 어떤 것들을 중점으로 생각해, 경험으로 정리하는것이 채용 시장에서 유리할까요?
2. 1차 MVP가 끝난 후엔, 각자 이전에 논의했던 2차 MVP 기능들 중, 본인이 원하는 기능을 구현하는 방식으로 진행하고 있습니다. 그러다 보니, 작업의 영역이 통일되지 않고 중구난방으로 되게 되었습니다. 저같은 경우만 하더라도 JWT하다가, FAQ하다가, 지금은 실시간 인기 FAQ 를 하고 있습니다. 8명이서 작업을 분담하기가 까다로워서, 이렇게 진행했는데, 이런 식으로 업무를 나눠도 괜찮을까요? 아니면 팀원들마다 영역을 정하는 좋은 방법같은게 있을까요?

2. 현업에서 처음에는 서버를 1개를 사용하다가 추후에 증설하신 실제 경험이나 사례를 알고 싶습니다.

### 1. 사용자 알림은 어떤 기준으로 설계해야 하는가?

**질문**

서비스에서 알림이 발생하는 조건과 시점을 정리하고 있다. 실제 서비스에서는 사용자 경험을 고려해 알림의 시점과 빈도를 어떻게 설계하는지 궁금하다.

**멘토님 답변**

먼저 어떤 상황에서 언제 알림을 보내야 하는지 정하는 것이 좋다. 알림 수신 설정처럼 사용자가 통제할 수 있는 기능도 서비스 특성에 맞게 고려할 수 있다.

모든 알림을 즉시 보내기보다는 중요도에 따라 실시간으로 보내거나 여러 건을 묶어서 발송할 수 있다. 사용자 반응이 없다면 반복 발송을 줄이는 방식도 생각해 볼 수 있다.

사용자가 늘어나면 알림 발송량 때문에 지연이나 시스템 불안정이 발생할 수 있다. 각 알림이 반드시 필요한지, 즉시 보내야 하는지부터 구분하는 것이 좋다.

급하지 않은 알림은 서버 자원에 여유가 있는 시간에 한꺼번에 보내는 것처럼 일부러 늦출 수도 있다. 모든 알림을 보내기보다 꼭 필요한 알림에 집중하는 것이 핵심이다.

알림 빈도와 시점은 Duolingo와 LinkedIn이 공개한 사례를 참고해 보라고 추천하셨다.

**참고 자료** (멘토님이 언급하신 사례를 팀이 찾아 정리)

- Duolingo, [A Sleeping, Recovering Bandit Algorithm for Optimizing Recurring Notifications](https://research.duolingo.com/papers/yancey.kdd20.pdf) (KDD 2020): 매일 보내는 학습 리마인드 알림의 문구를 밴딧 알고리즘으로 고른다. 기존 방식보다 일일 활성 사용자가 0.5%, 신규 사용자 리텐션이 2% 늘었다고 보고했다.
- Duolingo 블로그, [Hi, it's Duo: the AI behind the meme](https://blog.duolingo.com/hi-its-duo-the-ai-behind-the-meme/): 위 논문을 쉽게 풀어쓴 글이다. 처음 보는 알림 문구일수록 효과가 크고 반복할수록 떨어져서, 최근에 보낸 문구는 다시 보내기까지 간격을 둔다.
- [Duolingo Research](https://research.duolingo.com/): 35일 동안 보낸 리마인드 알림 2억 건의 데이터(사용한 문구, 2시간 안에 학습했는지 등)를 공개했다.
- LinkedIn 블로그, [Sending less email is just the beginning](https://blog.linkedin.com/2015/11/10/sending-less-email-is-just-the-beginning) (2015): 이메일 발송량을 절반 가까이 줄이고 불만은 65% 넘게 줄였다. 짧은 시간에 들어온 초대 여러 건을 메일 한 통으로 묶는 등, 알림을 한곳에서 관리하는 플랫폼(ATC)을 소개한다.
- LinkedIn 엔지니어링 블로그, [Air Traffic Controller: Member-First Notifications at LinkedIn](https://engineering.linkedin.com/blog/2018/03/air-traffic-controller--member-first-notifications-at-linkedin) (2018): 모든 알림을 ATC로 모으고, 회원마다 어떤 알림을 언제 어느 채널로 보낼지 정하는 구조를 설명한다.

### 2. 관리자 알림과 개발자용 모니터링 알림은 어떻게 구분하는가?

**질문**

실무에서 관리자에게 메일을 보낸다고 했는데, 개발자가 확인하는 로그와 별도로 운영하는 것인지 궁금하다. 우리 프로젝트에도 관리자 알림이 필요한지 알고 싶다.

**멘토님 답변**

멘토님이 설명하신 관리자 알림은 개발자가 아니라 고객사의 관리자나 감사 담당자에게 보내는 알림이다. 개발자용 로그는 별도로 수집한다.

B2B 서비스에서는 고객사에 특정 정보가 다운로드됐다는 사실 등을 안내할 수 있다.

현재 프로젝트처럼 B2C 서비스라면 사용자 행동을 모두 모아 관리자에게 메일로 보낼 필요는 크지 않아 보인다. 서비스 장애나 이상 징후를 확인하는 모니터링 알림이 더 유용할 수 있다.

### 3. 장애 공지에서는 표현과 안내 방식을 어떻게 정해야 하는가?

**질문**

장애 안내 배너 기능을 구현했는데, 기업에서는 ‘장애’라는 표현에 민감할 수 있다는 피드백을 받았다. 실제로도 그런지, 공지는 어떻게 처리하는지 궁금하다.

**멘토님 답변**

장애 상황에서는 안내가 얼마나 빠르게 이루어지는지도 중요하다. 다만 안내 범위와 표현은 상황에 따라 달라진다.

멘토님의 회사에서는 빠르게 해소된 문제는 관련 고객사에 안내하고, 장기화될 것으로 예상되면 배너 등으로 알리기도 한다. 외부 클라우드나 다른 서비스에서 발생한 문제라면 그 상황도 고객사에 전달한다.

서비스 수준 약정인 SLA나 장애 대응 보고서와 연결될 수 있어 표현에 민감한 편이다. SLA는 서비스가 얼마나 장애 없이 운영되는지에 대한 약속이라, 지키지 못하면 비용으로 보상해야 하는 경우도 있다. 그래서 공지에 장애 원인을 자세히 설명하지는 않는 편이다.

공지는 개발자가 직접 올리는 경우가 드물다. 사업부나 온보딩 담당 부서가 현황을 파악하고, 기획 쪽에서 안내 방식을 결정하는 편이다.

배너를 띄워도 사용자가 잘 보지 않을 수 있으므로, 배너만으로 충분히 전달된다고 생각해서는 안 된다.

### 4. 서버는 처음부터 여러 대로 구성해야 하는가?

**질문**

현재 프로젝트는 서버 한 대로 시작하고 필요하면 늘리려고 한다. 실무에서도 이런 방식으로 시작하는지, 처음부터 여러 대를 고려해야 하는지 궁금하다.

**멘토님 답변**

멘토님이 설명하신 실무 운영 환경에서는 기본적으로 서버를 두 대 이상 구성한다. 처음 두 대를 두는 주된 이유는 처리 성능보다 장애에 대비한 가용성 확보에 가깝다.

다만 교육 프로젝트에서는 처음부터 이중화를 완성하기보다 한 대로 MVP를 완성하고, 이후 개선 과제로 확장해 보는 것을 추천한다.

서버를 늘리면 로드밸런서뿐 아니라 DB와 Redis의 장애 대응도 함께 고민하게 된다. 단순히 서버 수만 늘리는 작업으로 끝나지는 않는다.

두 대에서 세 대, 네 대로 늘리는 단계에서는 사용자 증가에 따른 부하 분산과 처리량 확보가 더 큰 목적이 될 수 있다. 메일 서비스처럼 사용자가 아주 많은 서비스에서는 사용자별로 DB를 나눠 운영하는 사례도 있다고 소개하셨다.

서버 한 대에서 시작해 점점 늘려 가는 과정은 멘토님이 공유하신 [안정적인 서비스 운영: 설계에서 모니터링까지](https://www.slideshare.net/slideshow/201403/32157322) 슬라이드에서 볼 수 있다. 단일 서버의 한계, 웹 서버 증설과 로드밸런싱, DB 이중화, 세션을 외부 저장소로 옮기는 과정을 다룬다.

### 5. 장애 시나리오는 어떻게 만들고 우선순위를 정해야 하는가?

**질문**

프로젝트에서 발생할 수 있는 장애 상황을 어떻게 작성해야 할지, 어떤 상황부터 대응해야 할지 감이 잡히지 않는다.

**멘토님 답변**

사용 중인 구성 요소별로 “이것이 멈추면 어떻게 되는가?”를 질문하면서 상황을 나열해 보는 것이 좋다.

예를 들어 DB·Redis·LLM 서버의 중단, 요청 증가에 따른 부하, 외부 서비스 지연으로 인한 요청 누적, 클라우드 장비의 재부팅 등을 생각할 수 있다.

멘토님이 겪으신 레거시 사내 시스템에서는 Tomcat 프로세스가 죽어도 자동으로 다시 실행되지 않는 문제가 있었다. 장비 자체가 죽는 상황도 생기므로, 프로세스가 종료되거나 서버가 재부팅됐을 때 서비스가 자동으로 다시 실행되도록 구성해 두어야 한다. 다른 서비스 때문에 우리 서비스에 장애가 나는 경우도 함께 고려한다. 원인 분석을 위해 로그나 힙 덤프를 남기는 방법도 있다.

모든 장애를 없애기보다는 사용성을 최대한 유지하는 것이 목표다. 시나리오를 목록으로 만든 뒤 팀에서 중요도를 논의해 순서대로 대응하면 된다. 이 단계에서는 누구든 아이디어를 던져 보는 것이 중요하다.

### 6. 장애가 발생한 작업은 반드시 재시도하거나 복구해야 하는가?

**질문**

장애 대응에서 재시도, 복구, 데이터 정합성을 어디까지 보장해야 하는지 궁금하다.

**멘토님 답변**

모든 실패를 반드시 재시도해야 하는 것은 아니다. 서비스의 중요도와 정책에 따라 처리 방식이 달라진다.

예를 들어 알림 큐가 쌓여 발송에 실패했다면, 한두 시간이 지난 뒤에도 보내야 하는 알림인지 판단해야 한다. 중요하지 않은 알림은 생략하고 반드시 전달해야 하는 알림만 다시 보낼 수도 있다.

데이터 정합성은 고려해야 하지만, 실패한 작업의 복구 범위와 재처리 여부는 팀에서 정책으로 정리하는 것이 좋다.

### 7. 구현 방법이 잘 통하지 않을 때 언제 다른 방법으로 전환해야 하는가?

**질문**

FAQ 답변에서 질문과 관련 없는 내용을 제거하려고 형태소 분석을 시도했지만, 정상적인 답변까지 제거되는 문제가 있었다. 며칠 동안 시도한 방법을 언제 포기하고 다른 방법으로 바꿔야 하는지 궁금하다.

**멘토님 답변**

너무 오래 혼자 붙잡고 있기보다는 하루 이틀 정도 시도한 뒤 막힌 지점을 정리해 공유하는 것이 좋다.

목표가 무엇인지, 어떤 방법을 시도했는지, 각 방법에서 어떤 문제가 발생했는지, 현재 선택 가능한 대안은 무엇인지를 설명하면 된다.

실무에서는 미결 사항을 자료로 간결하게 정리해 상사에게 보고하고 판단과 조언을 요청하며, 지금처럼 팀 프로젝트라면 팀원들에게 의견을 구하면 된다. 당장 해결하기 어렵다면 미해결 과제로 남기고 다른 작업을 먼저 진행하는 선택도 가능하다.

시도한 방법과 실패 이유는 기록해 두면 이후 프로젝트 경험을 설명할 때도 도움이 된다.

### 8. 챗봇 답변에 포함된 부가 설명은 모두 제거해야 하는가?

**질문**

사용자가 요금제 변경 가능 여부를 물었는데, FAQ에 함께 있던 결합 할인 정보까지 답변에 포함된다. 질문하지 않은 내용은 모두 제거하는 것이 좋은지 궁금하다.

**멘토님 답변**

질문에 대한 핵심 답변을 제공하면서 관련된 부가 설명을 덧붙이는 정도라면 괜찮을 수 있다. 실제 상담에서도 질문에 답한 뒤 사용자가 추가로 궁금해할 내용을 설명하기도 한다.

따라서 질문에 직접 등장하지 않았다는 이유만으로 모든 내용을 제거할 필요는 없다.

다만 질문과 관계없는 내용이나 비슷한 설명이 반복되는 문제는 별도로 살펴봐야 한다. 어떤 내용을 불필요한 답변으로 볼지 팀의 기준을 정하는 것이 필요하다.

### 9. 답변 검증에 LLM을 한 번 더 사용하는 것이 좋은가?

**질문**

최종 답변을 검증하려고 하지만, 코드로 문장을 제거하면 의미가 왜곡될 수 있다. LLM으로 다시 검증하면 신뢰도와 응답 시간이 문제가 되는데 어떻게 접근하면 좋을지 궁금하다.

**멘토님 답변**

명확한 규칙 위반이나 개인정보 포함 여부처럼 코드로 확인할 수 있는 부분은 우선 걸러야 한다.

반면 답변이 질문의 의미와 연결되는지 판단하는 작업은 단순한 하드코딩보다 LLM의 재검증이 필요할 수 있다. 다만 모든 답변을 다시 검증하면 시간과 비용 부담이 생긴다.

재검증이 필요한 답변을 구분할 기준이 있다면, 해당하는 경우만 LLM에 맡기는 방식도 생각해 볼 수 있다.

대화에서는 유사도에 따라 바로 채택할 범위와 추가 판단이 필요한 범위를 나누는 아이디어가 나왔으며, 구체적인 방식은 여러 방법을 시도해 보기로 했다.

### 10. 개발용 데이터와 최종 평가용 데이터는 어떻게 구분해야 하는가?

**질문**

FAQ와 사용자 질문을 활용해 기능을 개선하고 있는데, 같은 데이터를 개발과 평가에 함께 사용해도 되는지 궁금하다. FAQ 자체가 변경될 수 있어 데이터를 나누는 기준도 모호하다.

**멘토님 답변**

같은 데이터에 맞춰 계속 수정하면 그 데이터에서는 잘 동작해도 새로운 사용자 질문에는 대응하지 못할 수 있다. 개발에 사용하는 데이터와 마지막에 확인하는 데이터를 구분하는 것이 좋다.

사용자는 FAQ에 적힌 문구 그대로 질문하지 않는다. 팀원마다 다른 표현으로 질문을 만들고, 문구와 띄어쓰기가 달라진 경우도 개발 과정에서 확인해 보는 것이 필요하다.

어느 정도 안정화되면 정해 둔 최종 평가 기준으로 확인하고, 실패 사례는 유사한 개발용 사례를 만들어 개선하는 방식으로 접근할 수 있다. 팀 차원에서 반드시 통과해야 할 기준도 정해 두는 것이 좋다.

다만 대화에서는 FAQ 원본과 개발·평가 데이터의 구체적인 구분 방식에 대한 해석 차이가 끝까지 남았다. 주제별로 나누는 방법이 합의된 것은 아니며, 팀 내에서 추가로 정리하기로 했다.

### 11. 코드 가드와 AI 가드는 어떻게 역할을 나누는 것이 좋은가?

**질문**

입출력 검증을 코드로 계속 보완할지, AI 가드를 파인튜닝해 사용할지, 두 가지를 섞을지 판단하기 어렵다. 어떤 방식이 적절한지 궁금하다.

**멘토님 답변**

명확한 규칙으로 판단할 수 있는 항목은 코드 가드로 먼저 처리하는 것이 좋다.

예를 들어 입력 길이, 개인정보 패턴, 정해진 욕설 목록, 지원 언어처럼 코드로 분석할 수 있는 조건이 있다.

이런 검사를 통과한 입력에 대해 AI가 필요한 판단을 수행하도록 역할을 나누는 방식이 적절해 보인다.

### 12. 외부 AI 가드와 자체 LLM 검증은 어떻게 비교해야 하는가?

**질문**

이미 제공되는 가드 시스템을 사용할지, 자체 LLM을 한 번 더 호출해 검증할지 궁금하다.

**멘토님 답변**

여러 후보를 실제로 비교해 보고, 우리 서비스의 데이터와 요구에 맞는지 확인하는 것이 좋다.

탐지 성능뿐 아니라 비용, 운영 부담, 놓치는 예외 사례도 정리해야 한다. 로컬에서 처리하는 방식과 외부 서비스를 호출하는 방식의 차이도 함께 고려할 수 있다.

외부 API를 사용하는 가드는 데이터가 외부로 전송될 수 있으므로, 실무에서는 보안 검수를 거친 뒤 사용하게 된다.

### 13. 개인정보는 출력에서 마스킹하면 충분한가?

**질문**

최종 답변에 개인정보가 포함되면 마스킹하는 출력 가드를 구현하려고 한다. 이 방식으로 처리해도 되는지 궁금하다.

**멘토님 답변**

먼저 챗봇이 개인정보를 입력받아야 하는 기능인지 확인해야 한다.

개인정보를 받을 필요가 없다면 LLM에 전달되기 전 입력 단계에서 차단하는 것이 좋다. 필요에 따라 내용을 제거하거나 마스킹하고, 개인정보를 처리하지 않는다는 안내를 줄 수도 있다.

별도 화면에서 개인정보를 입력하도록 유도하는 방식도 가능하다. 구체적인 처리는 팀에서 정한 정책에 맞추면 된다.

### 14. AI 기술을 사용했다는 사실이 프로젝트 평가에 도움이 되는가?

**질문**

AI 가드 같은 기술을 사용한 경험이 프로젝트 평가나 채용에서 긍정적으로 작용하는지 궁금하다.

**멘토님 답변**

기술을 사용했다는 사실만으로 가점이 된다고 보기는 어렵다. 왜 사용했는지 명확한 이유와 비교 근거가 있는지가 중요하다.

어떤 대안과 비교했고, 어떤 결과를 보고 선택했는지 설명할 수 있어야 한다. 외부 API라면 데이터 전송과 보관, 운영 문제와 비용까지 고려한 자료가 있으면 좋다.

PRD와 ADR 같은 문서로 요구사항, 설계 이유, 검토한 대안을 남기는 것도 도움이 된다. 모든 사소한 변경을 문서화하기보다는 프로젝트 방향에 영향을 준 주요 결정부터 기록하는 것이 좋다.

### 15. 가드가 모든 예외를 막지 못하면 평가에서 불리한가?

**질문**

코드로 가드를 구현해도 새로운 예외가 계속 발견될 수 있다. 평가 중 처리하지 못한 입력이 나오면 문제가 되는지 궁금하다.

**멘토님 답변**

완벽하게 모든 상황을 처리하는 서비스는 어렵다. 중요한 것은 처리하지 못한 상황에 대한 후속 대응책이 있는지다.

예를 들어 실패 사례를 로그로 수집하고, 일정 기준을 넘으면 확인하거나 대응할 수 있는 구조를 설명할 수 있다.

현재 구현의 한계를 알고 있고 이후 데이터를 모아 개선할 방법을 준비했다면, 반드시 감점으로 이어진다고 보기는 어렵다는 의견이었다. 다만 실제 평가 결과를 보장한 것은 아니다.

### 16. 개선을 위해 로그와 데이터를 수집할 때 무엇을 고려해야 하는가?

**질문**

실패 사례를 수집해 개선하려고 한다. 로그와 데이터를 남길 때 추가로 고려해야 할 사항은 무엇인가?

**멘토님 답변**

수집한 데이터는 서비스 개선에 활용할 수 있는 자산이지만, 모든 정보를 그대로 남겨서는 안 된다.

개인정보가 포함된 로그는 마스킹하고, DB에 보관해야 하는 민감한 정보는 암호화하는 방식 등을 고려한다. 보관 기간이나 회원 탈퇴에 따른 삭제가 필요한 정보도 있을 수 있다.

수집 여부뿐 아니라 누가 접근할 수 있는지, 어떤 형태로 보이는지, 언제 삭제할지까지 생각해 보는 것이 좋다.
